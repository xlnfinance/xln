# Use Hardhat Ignition for recoverable stack deployments

XLN will use Hardhat Ignition as the recovery-aware executor inside a standalone Stack Deployment module. The CLI/config entry point and any Stack Manager caller share that implementation. Retain XLN's artifact evidence, exact on-chain verifier and Hanko authority checks; jurisdiction discovery admission consumes the verified result separately. Extending the custom JSONL into a second scheduler would duplicate recovery semantics, while Foundry would introduce a second deployment/compiler path with stricter nonce-sensitive resume behavior.

After the Ethereum Sepolia attempt was interrupted with four successful creations, the owner chose to abandon it and design a Fresh Stack Deployment through Ignition. Preserve the old contracts without importing, resuming or overwriting them. The owner deleted their local receipts/journal and other prior deployment-task artifacts on 2026-11-13; this supersedes the earlier preservation instruction for those abandoned records. Future attempts retain their required native recovery evidence. The earlier plan to finish both testnets before migration was superseded: prove interruption/resume locally before public execution. The CLI recovery implementation and both separate public deliveries now have recorded results in the [operator guide](../deployment/ignition-stack-design.md#delivery-and-limits). Deleted artifacts do not certify a later candidate.

Owner decision, 2026-11-11: retain one confirmation between deployment operations and require at least twelve confirmations for all eleven winning receipts before catalog admission. This avoids repeating the full admission wait between every dependent operation while accepting greater reorganization exposure during construction. Prove reorganization handling and canonical receipt/block-hash checks before public execution; a journal success alone is insufficient. The twelve-block policy is not protocol finality.

Owner refinement, 2026-11-12: Stack Deployment succeeds after exact verification under the agreed 1/12 policy and preservation of its verified result. It does not require or perform jurisdiction catalog admission. The standalone module stays in this repository and reuses canonical Hanko, compiler artifacts and XLN checks; a separate repository or package is not required. This refines the earlier Stack Manager ownership decision. The owner confirmed all seven design decisions and requested the specification/ticket update; the extraction itself is not implemented by this planning publication.

The owner also selected native Ignition files plus one terminal JSON summary of the verified deployment, transaction references, actual expenses and artifact links. It is reporting evidence, not another recovery authority. Network/RPC configuration uses standard Hardhat configuration and environment values; deployment parameters use JSON. Private keys stay in the existing secret channel.

Malformed commands or configuration fail on stderr with a nonzero exit code. After a valid attempt is established, caught operation errors are recorded in the terminal result. Uncatchable process termination may prevent a final write; the native journal determines recovery. Private execution RPC endpoints with provider credentials are allowed through environment values, with secrets excluded from logs and artifacts. These choices do not authorize disclosure in later discovery publication.

The owner selected a native Hardhat task as the standalone entry point. It owns preflight, the existing Ignition/Hanko execution, exact verification and result writing within the Hardhat environment. Bun remains an allowed command launcher rather than a separate deployment orchestrator. Stack Manager can invoke the same implementation through an adapter; its catalog and runtime integration are separate from deployment completion.

The module is configurable for compatible EVM networks, without a two-network limit. Initial acceptance remains Ethereum Sepolia and Arbitrum Sepolia with the selected existing USDC; each additional network requires its own compatibility/preflight evidence. The [specification](../../.scratch/ignition-stack-migration/spec.md) records the completed extraction and recovery work. Public deployment and application integration remain separate delivery tasks; public delivery has its own [recorded results](../deployment/ignition-stack-design.md#verified-public-deployments-2026-11-14).
