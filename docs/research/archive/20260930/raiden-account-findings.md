## Highest-value followups

1. **Deadline-budget production regression**, evidence gap/candidate, not a verified loss. Raiden mediator.py:90–111 and :735–789 switches from waiting to immediate public reveal at a remaining-lifetime safety threshold. xln already supports starter arguments, so importing another secret registry would duplicate an existing primitive. However, xln `core/entity/paybook/lifecycle.ts:13,66–75` waits a fixed 120s after observing a secret; `core/entity/scheduler/due-hooks.ts:46–57` defers another 120s if eight dispute starts fill the draft. Account admission needs only 30s enforcement reserve (`core/account/consensus/dispute/deadline-policy.ts:7,35–43`). Sequence: accept live upstream lock; settle downstream and learn secret; upstream withholds ACK; before the fixed timeout the upstream signed reveal deadline expires, or eight starts postpone reaction. Exercise this through real Runtime/WAL/J inclusion, compare secured rights on both legs. If reproduced, derive the existing scheduler deadline from the earliest signed lock deadline minus a configured J-inclusion budget; publish through the existing registry/start arguments and canonical outbox. No new durable oracle/cache. **Starter evidence works only if start is timely:** Account:1764/1797 binds evidence timestamp to J start; DeltaTransformer:278–286 checks that timestamp against the signed deadline. Finalize:157 independently queues public reveals, usually later. Test omitted from current ACK-timeout coverage, which asserts preparing the dispute rather than deadline-safe on-chain inclusion.
2. **Finish the custom-clause artifact before claiming implemented generalized superset**, actual implementation gap. `Account.sol:863–1032` already executes arbitrary signed staticcall clauses with per-token allowances. `core/protocol/dispute/proof-builder.ts:229–245` serializes existing subcontract entries. But `AccountSubcontract` has address/bytes/allowances only (`core/types/account.ts:95`); searches of AccountTx/EntityTx handlers found no wallet-authored clause admission/approval/CREATE2 execution path. `docs/counterfactual-transformers.md` is explicitly SPEC. Counterfactual has actual CREATE2 address derivation and deployment assertions (`packages/node/src/utils/create2-address.ts:30–79`; funding `test/create2.spec.ts:55–96`). Minimum artifact: compile a constructorless approved clause, independently reproduce bytecode/address, sign, restart, deploy only for dispute, enforce exact allowance-limited outcome. Then establish what generalized apps are deliberately outside xln's financial model.
3. **Remove stale skip-on-failure advice from SPEC**, verified documentation conflict. SPEC section 2.5 recommends skipping a faulted clause; actual `Account.sol:863–938` says a clause is the executable signed right and must fail finalization on missing code/revert/OOG/malformed return. Foundry `TransformerFaultModes.t.sol:122–153` explicitly asserts fail-closed. Skipping an option exercise clause could give the writer the raw signed balance despite a valid holder right. Preserve strict policy and require executable/admitted immutable clauses; do not convert rights to optional hints. A bad jointly signed clause can freeze settlement: allowances bound value movement, not liveness. Production code has a 2M post-call gas reserve, not the SPEC's proposed fixed 1M-per-clause policy.
4. **Measure watchtower service funding/inclusion under one correlated failure**, operational evidence gap. Raiden MonitoringService:112–167 binds signed reward to authentic TokenNetwork and latest proof nonce; :238–296 schedules eligible services; :303–363 pays after response and timeout from UserDeposit. xln already has narrower owner-authorized, tower-address/account/proof-bound encrypted remedies (`core/watchtower/last-resort-appointment.ts:121–175`) and latest appointment selection, so do not import Raiden's registry/token bureaucracy. Its default eligibility is final 20% of the signed sum (:231–253); `core/watchtower/action.ts` sends the transaction using towerWallet, with no implemented reimbursement found. `maxFeeToken/feeBudget` are accepted optional HTTP metadata, not evidence of a payment engine. Smallest experiment: real funded tower, owner offline, exact signed appointment, stale adversarial close, gas spike, eight+ simultaneous disputes, tower restart, prove latest counterproof inclusion before timeout. Then choose a simple service subscription or explicit funded gas arrangement outside RJEA; on-chain rewards would be a real new protocol choice.

Omitted: exhaustive all-history Raiden contracts/client revision changes; complete light-client/Python WAL crash replay; Perun EVM backend implementation (Go API is not contract proof); every arbitrary financial application's representation/liveness theorem; all gas schedules/hardware capacities; full upstream or xln test execution. This is a detailed bounded mechanism study, not evidence that every edge case across all projects is exhausted.

XLNC owner scope preserved: conventional stateful EVM J, lower block gas, ordinary rebalance/disputes, phone/laptop full nodes. None of these recommendations requires stateless witnesses, ZK, a new ledger, or changed J/E/A ownership.
