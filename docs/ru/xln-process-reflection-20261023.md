# Разбор ошибок управления XLN — 23 октября 2026

Это разбор подтверждённых ошибок по сохранённым отчётам и истории управления.
Полный расход всех исполнителей за неделю не восстановлен; неизвестные расходы
и незакрытые резервы не считаются нулевыми. Документ не является сертификатом релиза.

## Что я сделал неправильно

1. Подменял выпуск закрытием отдельных проверок, коммитами, обзорами и запущенными
   процессами. Пользователь продолжал видеть старый продукт. Критерий результата:
   проверенный пользовательский путь и подтверждённый опубликованный релиз.
2. Не удерживал один финальный неизменный SHA. Доказательства с разных версий
   оказывались рядом и могли выглядеть как общий зелёный результат. Каждый PASS
   относится только к своему SHA и точной команде; переносить его запрещено.
3. Сохранял отчёты в файлах без подтверждения, что сообщил результат владельцу.
   После остановки из-за лимитов продолжались пустые пробуждения. Сохранённый файл
   означает только сохранение; сообщение в чате фиксируется отдельно. Таймеры,
   остановленные владельцем, остаются выключенными.
4. Допускал противоречивое состояние отчёта: старый unit оставался RUNNING,
   остановленный E2E выглядел текущим, Studio main смешивался с GitHub main.
   После каждого перехода обновлять существующий report целиком и атомарно:
   Studio HEAD, GitHub main, публичные frontend/backend, исходники, активный handle,
   терминальный результат, первый блокер. Неизвестное явно UNKNOWN.
5. Раздувал контекст повторным чтением больших пакетов, каталогов инструментов,
   логов и инструкций. Фактический расход по задачам не был полностью сведён.
   Читать необходимый фрагмент один раз, передавать короткий handoff, не запускать
   повторный модельный вызов после неизвестного исхода. Подписка не оправдывает
   бесполезные запросы; исторические резервы и запрет redeem сохраняются.
6. Обзоры моделей принимались за продвижение к аудиторскому одобрению. Полученные
   замечания требуют независимой проверки, исправления и повторения артефакта.
   Количество обзоров и прочитанных файлов не означает безопасность релиза.
7. Расширял работу на инструментарий и новые проверки до закрытия первой реальной
   денежной ошибки. После первой доказанной причины нужны минимальный L1,
   production-equivalent L2 и повтор исходного артефакта. Затем следующая причина.
8. Ошибочно задал полному unit лимит 180 секунд, хотя сохранённый такой же прогон
   занимал 1151,65 секунды. Он был убит управляющим лимитом, а не семантическим
   провалом. Перед запуском смотреть существующую команду, фактическую длительность
   и разрешённый бюджет. Не увеличивать сроки отдельных тестов ради PASS.
9. Диагностика PATH могла выглядеть как дефект финансового/PID-протокола: forge
   отсутствовал в non-login PATH. Полный PATH Studio включает Bun, local, Foundry,
   Cargo, Homebrew и системные каталоги. Проверять первую причину по evidence.
10. Форматирование переносило существующий lint-долг и добавляло новый. Нельзя
    просто заменить хеш baseline. Удалить новые нарушения; сокращение старого
    долга подтверждать точной разницей. Frozen-core approvals не менять.
11. В последнем handoff я смешал обычное падение check с блокировкой защитой.
    Исполнитель остановился на исправляемом ESLint-ошибке. Обычный красный тест,
    lint или сборка — задача для исправления. Реальные policy/frozen/usage/budget
    ограничения остаются обязательными, их нельзя обходить другим чатом/моделью.
12. Задавал владельцу общие вопросы о кошельках, не подготовив конкретный шаг.
    Владелец поручил turnkey-подготовку. Самостоятельно подготовить отдельные
    signer/keystore, unsigned deployment и расчёт стоимости. Конкретное действие
    с реальными деньгами требует ясного разрешения; testnet keys не переиспользовать.
13. Не давал честную оценку незавершённости вовремя. Владелец должен сразу знать:
    выпуск есть или нет, что изменилось для пользователя, первый блокер и нужное
    от него решение. Технические детали — только если помогают принять решение.

## Исполнение после разбора

Один писатель и один тяжёлый стенд на Studio. MacBook — только контроль.
Перед handoff проверить терминальный статус прежнего писателя, сохранённые
артефакты и активные handles. Не сбрасывать старые Goal, лимиты или учёт.

Сначала исправить отказ текущего check без ослабления baseline. Затем закрыть
подтверждённую ошибку срока/авторизации выплаты вклада. Досрочный запрос и полная
выплата после maturity должны соответствовать существующим подписанным условиям,
включая повтор, обе стороны Account и восстановление.

После закрытия подтверждённых финансовых замечаний выбрать один финальный SHA.
На нём пройти все исходные финансовые пути, полный unit/test/check, полный E2E,
расширенный release и непрерывный часовой soak. Сохранить все исходные требования,
публичные native TRON/Nile и Ethereum доказательства, tutorial, reload/restart,
восстановление и документированный деплой/rollback. Mainnet-процент и дату не
выдумывать. Успешная публикация исходников отдельно от обновления работающего продукта.
