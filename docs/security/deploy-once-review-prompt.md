## What the system is (so you do not rediscover it)

- Reserve–credit bilateral accounts (RCPAN). Each pair (LEFT = lower entityId) has per-token `collateral` and `ondelta` on chain; the signed off-chain `offdelta` completes Δ = ondelta + offdelta = LEFT's allocation. Settlement splits collateral by Δ; any shortfall beyond collateral becomes an on-chain FIFO **unsecured debt** repaid only from the debtor's future reserve inflows (Depository._settleShortfall, enforceDebts, _spendableReserve).
- Owner decisions, not up for debate: credit limits are never enforced on chain (signing offdelta is consent); debt is unsecured by design; a 0-second dispute window is an intentional "same-block policy"; the reference implementation is core/ (TS) and must not be asked to change casually.
- Entities: EntityProvider is the identity root. Numbered entities have id = bytes32(entityNumber) and a treasury at address(uint160(entityNumber)); lazy entities have id = keccak256(abi.encode(Board)). **Hanko** = recursive, stateless M-of-N proof: EOA signatures are leaves, claims reconstruct board hashes, verified against the current board (or the previous board for 7 days, dispute evidence only). Governance lanes replace a board: CONTROL (Hankos of entities holding control shares in Depository reserves, > 50% of fixed supply) > BOARD (current board Hanko) > DIVIDEND (EOA signatures weighted by live ERC1155 dividend balance) > FOUNDATION (entity #1 Hanko), each with a block-count delay from EntityArticles.
- Disputes: start with the counterparty's signed ProofBody at nonce N plus the starter's frozen transformer arguments (two precommitted blobs: for N and for exactly one named newer branch); counter-dispute locks a newer signed state before T; finalize at/after T = start + leftResponseSeconds + rightResponseSeconds. Transformers (DeltaTransformer: HTLC payments, partial-fill swaps, cross-jurisdiction Pulls resolved via a hash-ladder reveal registry) are STATICCALLed with the dispute context and return new deltas, clamped by signed allowances.
- Batches: processBatch(encodedBatch, hanko, nonce) is permissionless to relay; the outer Hanko authenticates the entity; sequential entity nonce; flash-mints inside the batch are checked at the end. Depository deployed bytecode is 23372 / 24576 bytes (EIP-170) at solc 0.8.36, optimizer runs=1, viaIR; linked libraries (Account, HashLadderRegistry, DepositoryBounds, NftCustody) run by DELEGATECALL.

## The question

These contracts are meant to be deployed once per chain and **never upgraded**: no proxy, no admin, no migration. Given that, what must change BEFORE the immutable deployment, and what can safely be left? Judge every finding by "will this force a redeploy or strand funds/identities in 1, 5, 10 years", not by style.

Probe at least these hypotheses; confirm or refute each with file:line evidence, then add your own:

1. Signature agility: HankoVerifier accepts only secp256k1 ecrecover leaves. No ERC-1271 contract members, no P-256/RIP-7212 (passkeys), no hash-based/PQ path. If a board wants a passkey or a PQ key in 5 years, is the only option a new EntityProvider with new identities?
2. Identity root immutability: EntityProvider.bindShareDepository is one-shot. Does that bind the CONTROL lane of every entity to Depository v1 forever, so a Depository v2 can never carry governance weight? What is the minimal rebinding primitive that does not become a rug vector (e.g. Foundation-delayed, or per-entity choice)?
3. Treasury addresses: entity N's ERC1155 treasury is address(uint160(N)). For small N these are precompile addresses; OZ _mint runs the acceptance check only when `to.code.length > 0`. On a chain that later deploys code at such an address (new precompiles with code, system contracts, EIP-7702 delegation), does registration or release revert forever? Would a namespaced treasury address break Depository.onERC1155Received's `from == address(uint160(id))` check?
4. Time bases across chains: board delays use block.number (EntityArticles delays, activateAtBlock); disputes use block.timestamp seconds. On L2s block.number semantics differ (L1 number on Arbitrum, 2s/250ms blocks elsewhere) and sequencers control timestamp drift. Which of these makes a fixed constant wrong on some chain, and should everything be seconds?
5. Rebasing / non-standard tokens: reserves are stored amounts, deposits are measured by balance delta (fee-on-transfer safe). A positive-rebasing token leaves unaccounted surplus; a negative-rebasing token makes the Depository insolvent for that token with no recovery path. Is a "no rebasing" listing policy enough for an immutable contract, or is per-token share accounting required?
6. Token listing authority: registerExternalToken is gated by an immutable deployer EOA on every chain. Losing that key freezes the listing forever. What is the right immutable-safe authority?
7. Re-entrancy surface: enforceDebts is public without nonReentrant (internal callers rely on it). Listed-token callbacks (ERC777 hooks, ERC1155 receivers) during processBatch can call it while flash reserves are live. Is the final flashloan assertion a complete defence? Propose the minimal split (internal _enforceDebts + guarded public wrapper) and confirm it does not break internal paths.
8. Emergency board rotation: activateBoard is blocked for 7 days after any activation (previous-board grace). A compromised new board rules for a week. A single-slot design cannot both revoke B and preserve B-signed dispute evidence. Design the two-historical-slot variant and state its residual risk precisely.
9. Board preimage: proposeBoard, registerNumberedEntity(Batch), foundationRegisterEntity accept a blind hash; an unreachable threshold bricks the entity's current-board authority. Which ingress points must validate the Board struct, and what exact predicate (members > 0, weights > 0, sum(weights) >= threshold, ≤ 256 members, unique ids, first member EOA-range)?
10. Voting bases: CONTROL counts only Depository reserves against fixed 1e11; DIVIDEND counts live ERC1155 balances (flash-borrowable through any external lender) against fixed 1e11. Both lanes are dead while < 50% is issued. For immutability, pick: issued-supply denominators + block.number-1 checkpoints, or something simpler that cannot be gamed.
11. Domain separation and typed data: Hanko payloads mix abi.encodePacked with string tags ("ENTITY_TRANSFER"), abi.encode with a MessageType enum, and keccak domain constants. No EIP-712. Is there any cross-payload collision or truncation ambiguity? Would EIP-712 for the governance actions (human-signed) be worth the bytes?
12. Trailing-bytes tolerance: abi.decode tolerates extra trailing calldata. Can any signed blob (encodedBatch, ProofBody, transformer args) be padded to change meaning without changing the signed hash? Check every hash that commits to bytes versus decoded structs.
13. Dispute liveness under L1 stress: windows are fixed seconds; a censored or congested L1 (base fee spikes, inclusion delays) can eat a short window. Sprites-style timeouts extend under congestion; is a base-fee-aware or "any-block-since-start" extension worth adding for the finalize/counter paths, or does the response-window policy already absorb it?
14. Watchtower path: watchtowerCounterDispute has no bond, no reward, and appointmentSequence is not enforced on chain. For an immutable contract, is a revocation fence (per-entity high-water mark with owner-Hanko bump) required, or is removal cleaner?
15. Gas repricing risk: DepositoryBounds and the 15M-gas "liveness envelope", 176 KiB ProofBody, 256 KiB batch, 2M transformer reserve, 30k token-supply staticcall. Which constant breaks first if calldata/SSTORE/STATICCALL costs change (EIP-7623 already assumed), and should any be a Foundation-settable parameter with delay rather than a constant?
16. Value conservation: state the exact invariant that should hold per token (Σ reserves + Σ collateral + outstanding flash mints == external balance held, except rebasing) and whether foundry invariants in jurisdictions/test/foundry already cover it; propose Halmos/Certora properties for HankoVerifier (no proof accepted below threshold; no duplicate signer counted; previous-board only when currentOnly=false and within grace).
17. Anything else you would refuse to sign off on for an immutable deployment.

## Output format

For each item: `CONFIRMED / REFUTED / PARTIAL` + one-paragraph reasoning with file:line + verdict `MUST-FIX-BEFORE-DEPLOY / SHOULD / NICE / NO-ACTION` + the minimal concrete change (signature, storage, and roughly how many Depository bytes it costs; Depository has ~1.2 KB headroom, EntityProvider ~8 KB, Account ~6 KB). Then a ranked list of the top 5 by "probability × cost of a forced redeploy". Then the 3 things you would formally verify first. Terse, evidence-first, no restating the system description.
