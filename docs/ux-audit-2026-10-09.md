# Wallet user-flow audit — 2026-10-09

This is the initial audit snapshot. Follow-up implementation and current verification limits are recorded in the [Russian findings and fixes report](ru/ux-audit-2026-10-09.md); statuses and the verification table below describe the initial snapshot only.

Both wallets support basic local payments, receiving, same-network swaps and deposits. Neither is ready for an everyday first-time user: a settlement failure halted the shared hub, cross-network swaps failed, and Svelte lost visibility of a secondary network after unlocking. Several misleading balances and blocking browser dialogs were fixed during this audit.

This is a desktop local-testnet audit, not a claim of complete protocol correctness. The matrix records attempted flows and their observed outcomes. Dispute finalization, cross-network execution and disaster recovery did not reach successful terminal states.

## Scope and evidence

- Base commit: `4d8ee444c67c08df65922c04691456299b3358c0`, plus the uncommitted fixes described below. No commit or push was made.

## Super important — release blockers

### H1. A settlement error can halt the shared hub and connected wallets — FIXED IN CORE (2026-10-10)

**Observed:** H1 stopped with `RUNTIME_ENTITY_INPUT_APPLY_FAILED` and `SETTLEMENT_PROJECTED_COLLATERAL_RANGE`. The stack traverses `projectSettlementDeltaOverrides`, `buildPostSettlementDisputeProof`, `buildSettlementHankoDraft` and `materializeDeferredSettlementApprovals`. Connected wallets then exposed fatal peer rejection/runtime halt, and creating a fresh wallet failed with `HALTED_REQUIRES_OPERATOR`. Browser resets could not repair the shared hub; restarting the dev stand did.

Before the halt, the UI permitted a collateral withdrawal using credit-backed outgoing capacity even when collateral was zero. This is a plausible trigger, but the exact submitted request has not been correlated to the first failing frame; do not treat causality as proven. A later Svelte limit click exposed an already-halted hub rather than establishing that limit changes caused it.

**Fixed at the UI boundary:** withdrawal availability is now `max(outCollateral - outTotalHold, 0)`, shared by both frontends.

**Fixed in core (TS + Rust):** a `settle_transition` upsert now runs the post-settlement projection before its workspace is committed (TS `buildUpsertWorkspace`, Rust `apply_upsert`; same order: predecessor, compile, projection). A credit-only collateral withdrawal is rejected with `SETTLEMENT_PROJECTED_COLLATERAL_RANGE:token=<id>` in both engines, so deferred auto-approval never sees an unprojectable workspace. The proposer evicts a rejected upsert from its Account mempool instead of failing the Entity candidate; a peer-signed frame carrying one is a typed Account input failure with no mutation. On the previous code the same upsert committed (`ok: true`), which is the precondition for the logged stack. Regressions: `settlement-transition.test.ts` (direct reject both sides, proposer eviction, peer-signed frame) and Rust `upsert_rejects_credit_backed_collateral_withdrawal_without_mutation`; all three TS tests fail with the fix reverted.

Not proven: the exact first input. The diagnostic receipt named in the log was deleted with the dev stand reset, so correlation to a specific wallet request remains inferred.

Evidence: [first-halt log](evidence/ux-audit-2026-10-09/dev-first-halt.log), [new wallet blocked](evidence/ux-audit-2026-10-09/svelte-new-wallet-blocked.jpg), [corrected collateral limit](evidence/ux-audit-2026-10-09/svelte-collateral-limit-fixed.jpg).

### H2. Svelte secondary network disappears after unlock — OPEN

**Reproduction:** create/use Tron alongside Testnet, fund the Tron account, return to Testnet, reload and unlock. The switcher subsequently showed one network and one entity instead of two. Testnet state remained available.

This establishes a recovery/discovery visibility failure, not proven deletion of the underlying Tron state. An ordinary user experiences missing money/account access. Recovery must restore the full entity/network inventory and demonstrate both balances after reopening.

Evidence: [missing secondary network](evidence/ux-audit-2026-10-09/svelte-secondary-network-missing-after-unlock.jpg).

### H3. Cross-network swaps do not complete reliably — OPEN, setup race partly fixed

React first-use target preparation previously threw `RECEIVE_CAPACITY_ACCOUNT_MISSING`; retrying manually moved it forward. Both UI adapters now treat this transient condition as pending while canonical target setup is being applied. A fresh H2-target browser run verified creation on the first submission, then exposed a separate `OWNER_RUNTIME_MISMATCH` failure. The opposite direction previously reached a resting order, but never a fill during observation.

Svelte allowed a disputed receiving target and waited until timeout. React also lists disputed destinations. Reject unavailable targets before submission, provide eligible alternatives, and make the canonical two-network ownership path execute through completion. Translate internal errors into a user-facing recovery action while retaining diagnostic details.

Evidence: [React ownership failure](evidence/ux-audit-2026-10-09/react-cross-runtime-mismatch.jpg), [Svelte disputed destination](evidence/ux-audit-2026-10-09/svelte-cross-disputed-target.jpg).

### H4. Dispute states misrepresent availability and strand management — PARTLY FIXED

React displayed disputed balances as immediately spendable and allowed “finalize” before the challenge deadline, with a false queued message. Home send/receive capacity now excludes disputed accounts; premature finalization is disabled with its deadline. Account-detail raw capacity still needs consistent frozen-state wording.

Svelte's all-accounts-disputed state replaced the main workspace with Open Account. The dispute detail showed the countdown, but the normal management/finalization route was not accessible in that state. Opening H2 restored workspace controls. A user must be able to finish the dispute without opening another account.

Actual finalization was not tested: the observed challenge window was approximately 25 hours. The audit did not alter chain time or protocol deadlines.

Evidence: [fixed frozen capacity](evidence/ux-audit-2026-10-09/react-frozen-capacity-fixed.jpg), [fixed finalize guard](evidence/ux-audit-2026-10-09/react-dispute-finalize-fixed.jpg).

### H5. Recovery configuration can look complete without operational protection — OPEN

React successfully reported a stored backup, but the appointed tower stated automatic dispute response was disabled. Svelte displayed configured recovery/protection while still awaiting first upload; device registration emitted a raw provider error. The next version should distinguish configured, uploaded, verified-restorable and actively protecting, with one actionable next step for each. A real restore and tower response remain required before claiming recovery works.

## Explicitly unverified

Mobile layout/touch, actual 25-hour dispute finalization, successful two-leg cross-network execution, restoration from backup after total local loss, tower dispute rescue, mnemonic/import variants, multisigner governance, production/mainnet behavior, external hardware wallets and every error permutation were not completed. The ownership screen was inspected, not a multisigner round trip. Pool close was requested, not fully reconciled. These limits must not be presented as passing results.

Recommended order: fix and reproduce the H1 rejection boundary first (core fix landed 2026-10-10; browser re-run of the withdrawal scenario pending); repair secondary-network recovery visibility second; then complete cross-network execution and dispute lifecycle. Re-run the same browser scenarios against those fixes before expanding cosmetic work.


## 2026-10-10 follow-up: dispute and recovery terminal states

The earlier unverified status above is superseded for four local browser paths. React and Svelte each passed a real dispute through signed-window enforcement, finalization, reserve credit, and withdrawal of exactly 100 USDC to the owner's external address. Each also restored funded Account state in a fresh browser and committed a subsequent payment. Final isolated test durations were 17.6 s / 16.9 s for disputes and 21.5 s / 28.7 s for recovery (React / Svelte; stand startup excluded). All four passed without skips or mocks; the related fast suites passed 76 tests and 425 assertions.

Svelte backup starvation, invalid journal-tail uploads, repeated onboarding after restore, and the misleading default recovery-service preview were fixed. Closed-dispute labels now distinguish completion from an active freeze. Private-chain clock acceleration remains explicit: these runs do not prove real-time day-long waiting, native TVM, adversarial counterproofs, or an offline-browser tower rescue.

Evidence: [browser reports, transaction evidence and screenshots](../output/dispute-recovery-audit). Run `bun run test:dispute:e2e` and `bun run test:recovery:e2e` sequentially with the canonical dev stand stopped; each command owns the single stand lock.
