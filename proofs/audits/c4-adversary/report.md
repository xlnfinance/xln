# C4 audit — adversary / invariant-validity angle

- Date: 2026-08-26 (resumed 2026-08-27 after provider-side termination; all runs re-verified)
- Auditor angle: attack **validity** of the C4 invariants — do they prove what the
  report says, or do handler restrictions silently exclude the dangerous paths?
- Audited artifacts: commit `944353c7c` wave-1 files
  (`jurisdictions/test/foundry/{DepositoryConservation,TransformerAllowance,HankoThreshold,HashLadder}.invariants.t.sol`,
  `HalmosLemmas.t.sol`, `handlers/*`, `helpers/SettlementDeltasHarness.sol`)
  against contracts at `jurisdictions/contracts/` (byte-identical to pinned SHA
  `80924b035`, verified by `diff -r`).
- Complementary to `proofs/audits/c4-repro/report.md` (92/100, re-run angle). This
  audit does not repeat reproduction findings; it attacks what c4-repro did not:
  handler reach, clause coverage, oracle soundness, lemma selection.
- Scope discipline: read-only for contracts and wave-1 artifacts; the only write is
  this file.

## Verdict summary

**No unsound oracle found.** Every ghost model I could check formally
(conservation accounting, nonce ghost, Hanko backing lower-bound, clamp
reconstruction, ordered-pair slots) is a correct abstraction of the contract
semantics on the paths the handlers actually reach. The reproduction claims are
honest (independently confirmed, including a direct baseline run c4-repro could
not do — see "Provenance").

**But the handlers do not reach several of the most bug-prone clause families,
and in exactly the region where the repo's one known open divergence lives.**
The debt lifecycle (creation by shortfall, chunked enforcement, forgiveness) is
structurally unreachable in the conservation suite and unasserted everywhere;
settlement forgiveness is never generated by any handler; transformer coverage is
single-index/single-clause; the hash-ladder window model is symmetric and cannot
detect a left/right window-selection bug. One advertised invariant
(`invariant_debtNeverEntersValuePool`) is a byte-identical duplicate of another
and reads no debt state at all.

finals: Conservation ~5 accepted / ~22 rejected mixedBatch (of ~21/run, 2711

accepts, 4 clamp observations (2nd observed run: 5/2/2); HashLadder 6 disputes,
8 registrations accepted (3 Source + 5 target writes); HankoThreshold 11 accepted

observations per oracle — the vacuity findings below are **structural (shapes
never generated), not statistical (too few samples)**.

## Findings + severity

### A1 — HIGH (vacuous reach): debt lifecycle unreachable in the conservation model

`ConservationHandler.mixedBatch` builds batches only from flashloans,
externalTokenToReserve, R2R, C2R, settlements, R2C, external withdrawals
(`jurisdictions/test/foundry/handlers/ConservationHandler.sol:195-339` with
`XlnHanko.emptyBatch()`): `disputeStarts`, `counterDisputes`,
`disputeFinalizations`, `revealSecrets` are always empty.

Debts are created only by `_settleShortfall`
(`jurisdictions/contracts/Depository.sol:1055-1070` → `_addDebt`), reachable only
through `_applyAccountDelta` (:1016-1052) ← dispute finalization. With
finalization never generated, **no debt can ever exist in the conservation
model**, so `enforceDebts` (:748), `_reduceDebtOutstanding` (:630),
`_afterDebtCleared` (:622) and `_forgiveDebtsBetweenEntities` (:833) execute only
in their zero-debt no-op form. The finalization path's conservation is covered
only by `TransformerAllowanceHandler` in its narrow 1-token/1-clause dispute
shape (see A4).

Not an unsoundness — the invariants are true on the executed paths — but the
report's conservation claim reads far broader than the executed domain, and the
excluded region is precisely where the known DebtChunking divergence lives.

### A2 — HIGH (duplicate/vacuous invariant): `invariant_debtNeverEntersValuePool` reads no debt state

`jurisdictions/test/foundry/DepositoryConservation.invariants.t.sol:94-103` is
byte-for-byte the same assertion as `invariant_valuePoolIsConserved` (:73-82).
Neither touches `debtOutstanding`, `_debts`, `_activeDebtsByToken` or
`_debtIndex` — no debt state is referenced anywhere in the suite. The advertised
property "debt lifecycle paths may not leak into the value pool" is proven only
in the trivial sense that the pool equality holds on paths that (per A1) never
move debt. The report counts this as a distinct conservation invariant.

### A3 — HIGH (gap): settlement forgiveness never executed by any new handler

`ConservationHandler.sol:306` always sets `forgiveDebtsInTokenIds: new
uint256[](0)`; TransformerAllowance and HashLadder handlers have no settlement
action at all. The forgiveness admission loop
(`Depository.sol:514-529` → `_forgiveDebtsBetweenEntities` :833-858, including
the third-party-FIFO-head `E2` guard at :527) has **zero executed coverage** in
C4. Its only coverage in the repo is the frozen `DebtChunking.t.sol` — whose
semantic expectation currently fails (single-entry O(1) forgiveness vs full-drain
test; reclassification in the amended report matches my independent code
reading: `_assertBooksAgree` at DebtChunking.t.sol:212 passes, failure is the
full-drain assert at :213, residual = 2 intact FIFO entries × 100).

Consequence: the C4 "conservation holds" evidence says nothing about the one
code path with a live owner-triage question. No C4 invariant asserts debt
bookkeeping consistency (`debtOutstanding == Σ queue`, active-count, cursor) —
that property exists only inside the frozen test.

### A4 — MEDIUM (shapes): transformer coverage is single-index / single-clause

`TransformerAllowanceHandler._proofBody` (:158-185): `offdeltas` length 1,
`tokenIds` length 1, `transformers` length 1, allowance array length ∈ {0,1},
`deltaIndex` always 0. Halmos harness has the same shape
(`HalmosLemmas.t.sol:26-27`, `SettlementDeltasHarness.run`). Unexecuted shapes:

- **Multiple delta indices with partial allowances** — the gate loop
  (`Account.sol:996-1000`) must revert when ANY unallowanced `j` changes even if
  another index is allowanced. Never generated.
- **Multi-clause chaining** — clause 2's gate and clamp band are measured against
  clause 1's *clamped* output (`Account.sol:996,1002-1024`); a clause cannot
  claw back what a previous clause's band removed (and vice versa). Never
  generated.
- **Invalid allowance arrays** — duplicate `deltaIndex`, `deltaIndex ≥
  deltaCount`, `allowances.length > deltaCount` must all revert
  (`Account.sol:1121-1132`). Never generated (deltaCount is always 1).
- **Transformer fault modes** — `TransformerLivenessHarness` implements
  RevertCall/ExhaustGas/ShortReturn/WrongLength/MalformedReturn/ReturnBomb, and
  **no foundry test uses any of them** (repo-wide grep: only the hardhat TS
  dispute suite exercises `TransformerExecutionFailed` paths).
- **Argument-decoder path** — `_decodeTransformerArgumentList`
  (`Account.sol:1096-1110`): handlers and the halmos harness always pass `""`,
  so the staticcall decoder, its gas-gate revert (:1102-1104) and the
  malformed→empty soft-decode never execute in C4.

The two executed properties (gate iff changed; exact band clamp) are sound for
the shapes reached — but "transformer allowances hold" as a headline is proven
only for one-index, one-clause, empty-arguments, well-behaved-transformer
executions.

### A5 — MEDIUM (model symmetry): hash-ladder window side-selection untestable

`HashLadderHandler` uses `LEFT_RESPONSE_SECONDS == RIGHT_RESPONSE_SECONDS == 50`
(`handlers/HashLadderHandler.sol:30-33`). The owner-window selection
(`HashLadderRegistry.sol:68-70`: `entityId < counterparty ?
account.leftResponseSeconds : account.rightResponseSeconds`) therefore cannot
distinguish left from right: a bug that reads the *counterparty's* window passes
the invariant. The amended report states the "50s/50s" bound, but not that it
neuters side-selection. Also: the handler never finalizes a dispute, so
"dispute closed → first Source write is E12" is never exercised and `g.active`
never resets; the witness is always valid so the E9 forgery branch is unreached.

### A6 — MEDIUM (observation skip): clamp oracle blind after first shortfall

`TransformerAllowanceHandler.finalizeTransformed` skips all delta observation
when either party has outstanding debt in the token
(`handlers/TransformerAllowanceHandler.sol:343-361`, `if (!clean) return;`). The
`Δ_applied = Δreserve(L) − Δdebt(L) + Δdebt(R)` reconstruction is exact for all
three custody branches of `_applyAccountDelta` *given zero pre-existing debt*
(verified by hand against `Depository.sol:1034-1049`), so the skip is a correct
precondition — but nothing in the model ever repays debt (no settlement/R2R
actions; enforcement triggers only inside `seedCollateral`'s spendable check), so
after the first shortfall finalize, that token's observations are permanently
blind. Combined with A1: the debt↔delta interplay is observed only until the
first shortfall.

### A7 — LOW (halmos tolerance): sound in-model, but the justifying repro is uncommitted

The harness tolerates exactly one revert selector,
`TransformerGasBudgetUnavailable` (`helpers/SettlementDeltasHarness.sol:96-100`).
I verified the tolerance is tight *within the model*: with always-empty
arguments the decode-site gas revert (`Account.sol:1102-1104`) is structurally
unreachable (early return at :1097), leaving only the `_applyTransformer` site
(:887), which a real EVM caller with the configured 300M limit cannot hit first
in a 1-clause body; and no clamp/gate branch can emit that selector. Caveats:
(1) with ≥2 clauses a genuinely gas-starved second clause *would* legitimately
emit it, so the tolerance must not be copy-pasted into a multi-clause harness;
(2) the minimal repro (`check_gateZeroConcrete` — halmos FAIL / EVM PASS) cited
by the original report is **not in the committed file**, so the artifact claim is
re-verifiable only from the harness code, not from an artifact.

### A8 — LOW (lemma selection): the five lemmas are correct but narrow

What a full formal spec (Certora-class) would demand and C4 does not state:

1. Full-int256-domain clamp equivalence, including the ordered-sentinel branches
   (`Account.sol:1140-1159`: `lowerOrdered==0 → 1`, saturating upper, applied==0
   floor) — unreachable under the ±2^40 bounds.
2. Non-representable `ondelta + offdelta` (`_addSignedInt256` → `representable ==
   false`) must revert when transformers exist (`Account.sol:971`) — unreachable
   under the bounds.
3. Per-index gate quantified over allowance subsets and deltaCount ≥ 2 (see A4).
4. Clause-chaining residual-band lemma (see A4).
5. Allowance-array validity lemma (dup/out-of-range/oversized → revert).
6. `tokenIds` strictly-increasing admission (`Account.sol:1054`).

None of these is *claimed*, so this is gap-list material, not a false claim. The
nonce-lemma exclusion (ECDSA concreteness) is correctly argued and correctly
delegated to the stateful suite (A10).

### A9 — LOW (bounds): Hanko nesting depth ≤ 3, registered boards unexercised

`probe` builds 1–3 claims with backwards-only nested references
(`HankoThresholdHandler.sol:156,207-210`) vs `MAX_HANKO_CLAIMS = 64`
(`HankoVerifier.sol:27`); members 1–3 vs 256/claim; weights/thresholds 1–4 vs
uint16. The `_boardMatches` registered-board branch (`HankoVerifier.sol:240-246`,
`currentBoardHash != 0`) never executes — the handler never registers entities,
so every accepted proof is lazy (`entityId == boardHash`). The ghost lower-bound
is sound (verified: `verify` evaluates ALL claims — `HankoVerifier.sol:68-85` —
so on an accepted proof every nested member individually passed its own
threshold, making ghost-backing exactly contract votingPower). The
previous-board grace path is unreachable through `verifyCurrentHankoSignature`
(`currentOnly=true`, `EntityProvider.sol:612-617`) — fine for the processBatch
claim, but the dispute-evidence grace path
(`verifyHankoSignature`, `Account.sol:1711-1713`) has no C4 coverage at all.

### A10 — INFO (soundness verified): nonce ghost approach is sound

`entityNonces` has exactly one writer (`Depository.sol:340`), placed before
`_processBatch`; any body revert reverts the write atomically, so
"+1 on accept / 0 on reject" is structurally forced, and the handler's dual
oracles (per-batch step check `ConservationHandler.sol:145-155`; state-equality
invariant + brute-forced ghost-slot sensitivity control) check real state against
real state. Documented restriction stands: replay is tested only against the
*last* accepted batch per actor; historical-batch replay relies on the same
code path but is unexecuted. No path exists where the nonce advances without a
successful batch or vice versa.

### A11 — INFO: minor handler-restriction documentation errors

- The deposit `entity == 0 → credit batch initiator` rewrite
  (`Depository.sol:481-483`) is never exercised; the handler comment
  (`ConservationHandler.sol:217-219`) justifies avoiding it with a claim that is
  wrong for the processBatch path (crediting the caller address happens only in
  `adminRegisterExternalToken`, :675). Benign — the restriction is conservative —
  but the recorded reason is false and will mislead a future editor.
- `mixedBatch` external deposits always mint+approve fresh tokens, so the
  fee-on-transfer / partial-transfer re-measurement branch
  (`Depository.sol:690-695`, balance-delta re-read) is exercised only in its
  no-op form (ERC20Mock is exact).

### A12 — INFO: entry points entirely outside the C4 model (unclaimed, listed for completeness)

`watchtowerCounterDispute` (`Depository.sol:385-424` — a finalize-capable
entrypoint), `adminRegisterExternalToken` (:664-671), `onERC1155Received`
(:1075-1085), `revealSecrets` (:544-549), ERC721/ERC1155 custody legs, and the
public unauthenticated `enforceDebts` (:748) as a direct action. Coverage for
some exists in the hardhat TS suite; none in foundry invariants.

1. **Debt-lifecycle handler reach (A1/A3):** give ConservationHandler (or a new
   handler) dispute start/finalize actions and settlements with non-empty
   `forgiveDebtsInTokenIds`, so shortfall debt creation, chunked `enforceDebts`
   with non-zero queues, and forgiveness execute under the conservation oracles.
2. **Debt bookkeeping invariant (A2/A3):** port `_assertBooksAgree`
   (`debtOutstanding == Σ live queue`, active-count, cursor-only-zeroed-prefix)
   into a stateful invariant; today it lives only in a frozen failing test.
3. **Deduplicate or make real `invariant_debtNeverEntersValuePool` (A2):** assert
   something that reads debt state (e.g. pool equality unchanged across a
   forced forgiveness/enforcement cycle) or delete it and stop counting it.
4. **Transformer shapes (A4):** multi-index bodies with partial allowance
   subsets; multi-clause chaining (incl. "clause cannot exceed residual band");
   invalid allowance arrays; at least one fault-mode harness clause per
   stateful run; one lemma with non-empty argument wrappers to reach
   `_decodeTransformerArgumentList`.
5. **Asymmetric hash-ladder windows (A5):** LEFT=50/RIGHT=70 (any asymmetry) and
   a role-side assertion; add a finalize action so "dispute closed → Source
   E12" executes; add one invalid-witness action for the E9 branch.
6. **Debt-repay action in the allowance suite (A6):** mint + R2R/withdrawal to
   trigger `enforceDebts` so `clean` recovers and clamp observation resumes
   after a shortfall.
7. **Commit the gas-artifact repro (A7):** add `check_gateZeroConcrete` (halmos
   FAIL / EVM PASS) to HalmosLemmas.t.sol as a `forge`-only test, so the

   the tolerance is single-clause-only.
8. **Halmos breadth (A8):** full-domain clamp lemma with sentinel branches
   (bound to int256, loop caps adjusted), non-representable-input revert lemma,
   allowance-validity lemma.
9. **Hanko depth/width (A9):** one deep-chain probe (claims ≈ 8–16) and one
   registered-board probe (via EntityProvider registration) to cover
   `_boardMatches`' registered branch and `UnusedHankoClaim` reachability at
   depth.
10. **Historical-batch replay + deep profile (already listed by the report):**
    replay a non-last accepted batch; `FOUNDRY_PROFILE=deep` (1024×128) run.
11. **Fix the false comment at ConservationHandler.sol:217-219 (A11)** and note
    the fee-on-transfer deposit branch as unexecuted.
12. **Entry-point sweep (A12):** at minimum a conservation oracle around
    `watchtowerCounterDispute` (it is finalize-capable and Hanko-gated
    differently from `processBatch`).

## Grade

**78/100.**

- Soundness: 0 unsound oracles found; ghosts verified against contract semantics
  clause-by-clause; meta/sensitivity controls exist and fire; reproduction is
  honest and now baseline-proven. (No deduction for correctness of what runs.)
- −8: debt-lifecycle cluster (A1+A2+A3) — the suite's headline conservation and
  "debt never enters the pool" claims are proven on a model in which debt cannot
  exist, while the repo's one live owner-triage divergence sits exactly in the
  excluded region and one advertised invariant is a duplicate that reads no debt
  state.
- −5: transformer shape coverage (A4) — gate/clamp proven only for
  single-index, single-clause, empty-arguments, well-behaved transformers; the
  adversarial fault modes the frozen harness itself ships are unused in foundry.
- −3: hash-ladder symmetric-window blind spot (A5) + never-closed disputes.
- −2: clamp-oracle permanent blindness after first shortfall (A6).
- −2: uncommitted gas-artifact repro + single-clause-only tolerance caveat (A7).
- −2: lemma breadth vs a formal-spec bar (A8) and Hanko depth/registered-board
  bounds (A9).

Relative grading: c4-repro's 92 measures "does the evidence reproduce" — it does,
fully. This audit measures "does the evidence prove the claim's implied scope" —
for four of five goals it proves a materially narrower scope than the names
suggest, and the narrowing is silent (documented bounds exist for numbers, but
not for unreachable clause families). 78 reflects strong, honest, sound harness
engineering whose reach stops short of the dangerous paths.
