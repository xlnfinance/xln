### 2.4 C5 findings worth the owner's attention

1. **Capacity-sum conservation is NOT unconditional in the production
   formula.** Closed form `in = max(0, A−t)`, `out = max(0, B+t)`: when a
   clamp binds (e.g. `t < −B` after the transfer, i.e. sender's send
   potential exhausted mid-transfer), the `in+out` sum changes by exactly
   the clamp leakage. Conservation is exact (i) in the interior region and
   (ii) — the production-relevant case — whenever the transfer is covered by
   the sender's `outCapacity`, in which case the sender-side consumption is
   exactly `amount` with no leakage. The naive statement "a transfer
   conserves in+out capacity" is false at clamp boundaries within declared
   ranges (e.g. allowance larger than credit limit makes `B < 0`
   representable).
2. **TS `deriveDelta` summaries are view-independent**: `delta` (= `ondelta +
   offdelta`) and `collateral` are the same object for left and right views;
   the counterparty's negated position lives in the directional fields only.
   A right view that negated `delta` would not match TS.
3. **TS `addHold` (`core/account/tx/hold-utils.ts`) checks only `amount ≥ 0`
   — no unsigned upper bound**, while Rust `add_hold` enforces
   `≤ uint_max(256)` after the update. Mirror/proofs follow the Rust
   (stricter) semantics. Divergence is theoretical at 256-bit scale but is a
   real parity difference; flagged for the TLA/parity tasks.
4. Cross-width handler comparison at W12/W20 vs the fixed 16-bit mirror is
   meaningless by construction (different declared ranges ⇒ different
   rejection boundaries); neighboring widths therefore check transcription
   self-consistency instead.

## 3. C6 — radix, bounded universe (2-byte keys, ≤ 4 leaves)

Universe (all structurally distinct 2-byte keys): `0x0000, 0x0001, 0x00FF,
0xFF00` — exercises last-nibble divergence, first-nibble root fanout, and
extension compression. Value digests are an injective function of the key
(`[hi, lo, 0…0]`), so all hashes are real SHA-256 over distinct inputs.

### 3.2 Symbolic (Kani) status: harnesses written, toolchain does not converge

`radix_proofs.rs` contains the full symbolic harness set
(`c6a_all_permutations_same_root`, `c6a_subset_any_order_same_root`,
`c6b_delete_after_insert_is_identity`, `c6b_present_key_insert_is_noop`,
`c6c_different_leaf_sets_different_roots`, `c6c_empty_root_isolated`,
plus two-key fallbacks and a single-insert probe). Every configuration
attempted timed out inside CBMC symex — even ONE `updated()` call:

| # | Config | Result |
|---|---|---|
| 1 | default unwind (≈1000), 2-op harness | killed at 9.5 min, still transforming drop glue |
| 2 | `--default-unwind 75` (≥ sha256's 64-round loops) | 30 min timeout, still in symex (3,444 recursion-unwind events) |
| 3 | unwind 75 + per-function `--unwindset` capping the 5 recursive drop-glue functions at depth 3 (sound: no node frees while all maps are `mem::forget`-ed and persistent sharing keeps refcounts ≥ 1; unwinding checks left ON) | 9.5 min timeout |
| 4 | caps at depth 2 + OnceLock wait-queue loops capped, single-insert harness | 15 min timeout |
| 5 | pure canonical builder `build_radix16_merkle` (no Arc/OnceLock) | 9.5 min timeout (SHA-256 rounds + symbolic sort branches) |

Root cause: `Arc<Node>` drop glue is a 5-function recursive cycle containing
a 16-iteration array-drop loop, and sha2's compression needs loop unwind ≥
~70; their product explodes CBMC's symbolic execution on this
toolchain/CPU. This matches and concretizes the readme's Kani limitation
note ("никаких заявлений про BigInt/SHA"). The harnesses remain in the tree,
sound and ready, for a future toolchain or a Linux x86_64 runner with more
solver headroom.

### 3.3 Reviewed fact: `hash_branch16([]) == EMPTY_RADIX_ROOT` is unreachable via public map operations

Census over the pinned tree (review, not a proof):

- All 12 `make_branch` call sites pass ≥ 1 node:
  `persistent/node.rs:91` (ensure_root_branch, exactly 1), `:181`, `:199`,
  `:239` (put paths, 2 or ≥2), `:291` (delete collapse, ≥2 by match);
  `persistent.rs:862, 963, 1058, 1551` (batch roots, ≥1 — an existing root
  branch always retains ≥1 child), `:959, :1599` (≥2 by match arm), plus
  `compressed_parent` sites that return the lone child directly.
- `make_branch` fills `children` 1:1 from `nodes` (rejecting slot
  collisions), so a `Branch` always has ≥ 1 child.
- Map-side `hash_branch16` call sites receive that non-empty child list:
  `persistent/node.rs:142`, `persistent.rs:1460`;
  `radix.rs:213` (builder) is reached only with ≥ 2 buckets (a divergent
  nibble exists by construction of the shared-prefix split).
- `radix.rs:302` is a unit test. The only reachable `EMPTY_RADIX_ROOT` from
  a map is `root_hash()` of an empty map (`persistent.rs`, `root == None`).

Consequence: no `PersistentRadixMap` operation sequence produces a zero-child
branch, so the `hash_branch16([]) → EMPTY_RADIX_ROOT` edge cannot alias a
non-empty tree's root through an empty-children branch hash. Within the
reviewed pinned sources; not a machine-checked claim.
