# JEV harness hygiene: state, questions, confidence, and failure

Opened from the index at https://docs.typesafe.ai/llms.txt on 2026-10-03. Pages opened are cited inline. Example numeric thresholds on those pages are examples for that page's scenario, not a default for every harness. The Confidence page says the correct threshold depends on the domain. Cookbook-measured cutoffs were not collected.

## What is legal state?

### Takeaway
Legal `state` is text: a string, a JSON object, or an array of text values. Images, audio, video, and binaries are not inputs. There is no code-execution input. A recorded tool result is legal only after the harness turns it into that text or JSON. Jev 1.13's published size cap is 64k tokens for the whole request and 32k for `state` plus the longest question.

### Cited Findings
- State is the content evaluated. One request evaluates one state against one or more questions. All questions see that same state and are evaluated independently. Choice, Score, and Noul may be mixed. — [State](https://docs.typesafe.ai/concepts/state.md), opening and the paragraph under the title.
- "The simplest state is a plain string." State may also be "a JSON object or array containing related context." The format table lists string (a message, article, or passage), object (named fields, related records, or application state), and array (a sequence of messages or records). The array example is `["Hi", "My customer number is TS1337.", "My card was charged twice."]`. "Use an object for most requests so each part of the state has a descriptive name." — [State](https://docs.typesafe.ai/concepts/state.md), heading "State can be a simple string or a structured JSON value".
- "Jev accepts text only. State must be a string, JSON object, or array of text values. Images, audio, and video are not supported (yet)." English is the primary training language; other languages, including CJK, are accepted at lower accuracy. — [State](https://docs.typesafe.ai/concepts/state.md), note under that heading. The same text-only limit is repeated under [System One](https://docs.typesafe.ai/concepts/system-one.md), note after the opening.
- The worked state on that page is one JSON object holding a ticket (subject plus an array of `{from, text}` messages), an order (`id`, and `charges` with numeric `amount_usd` and string `status`), and a `refund_policy` string. "Put related information together when the decision requires comparing those parts." "The state contains the content and supporting facts." Questions stay out of state. — [State](https://docs.typesafe.ai/concepts/state.md), the support-conversation example and heading "Separate content from questions".
- The HTTP field is `state`, type `string | object | array`, required: "A plain string for text, or structured data (object/array) for things like chat logs, records, or the current state of your application." — [API reference](https://docs.typesafe.ai/api.md), heading "Evaluation endpoint".
- Current model row for Jev 1.13 (`jev-1.13.0`): "Context length | 64k tokens per request; 32k tokens for `state` plus the longest question." "Input | Text only. String, JSON object, or array of text values. No image, audio, or video input." The following bullets: the 64k budget "covers the `state` plus all questions combined"; the 32k budget "applies to the `state` plus the single longest question." "Jev evaluates natural-language text. Pre-process non-text inputs (images, audio, video, binaries) into text or structured fields before sending them as `state`." — [Models](https://docs.typesafe.ai/models.md), heading "Current models".
- Rate limits on that same row: "100K tokens per second / 80 requests per second." A request over either limit returns `429 Too Many Requests`. "Rate limits are adjusting dynamically" and "can change without notice." — [Models](https://docs.typesafe.ai/models.md), "Current models" and the warning under it.
- "Include only the context relevant to the current questions." Do not rely on knowledge in the weights when the current fact can come from the harness's own data. — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), step "Decompose the input state".
- For `jev-1.13`, "Accuracy falls as the state grows with content unrelated to the decision." "Context length limit. `jev-1.13` has a bounded context window. See the Models page for the exact token limits." "Giving it more context in `state` than the question needs" is listed to avoid, because of context rot. — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), heading "Large state full of irrelevant detail" and the closing Info. Note on that page: applies to `jev-1.13`, last reviewed 2026-10-02.
- "State is data, and `jev-1.13` does not treat it as hostile by default." Injected instructions, misleading framing, or text that argues for its own classification "can move the answer." — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), heading "Adversarial content".
- A tool-call trace is shown as ordinary JSON inside `state` (`trace.tool_calls`, `trace.tool_results`), then judged by separate Noul questions. The page does not describe executing those calls. — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), step "Decompose the questions", accordion "Example: verify a tool-call trace".
- "System One is TypeSafe's model for building AI-powered software, not agents. It does not generate code or choose its own next action." — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), opening paragraph.

### Inferences
- A harness may put a tool result into `state` only as text or as JSON fields. The docs show that shape in the tool-trace example. They do not define a tool-result type, and they do not say the model calls the tool.
- Nested objects, numbers, and arrays of records appear inside the State page's object example, while the limit sentence says "array of text values." The safe reading of the limit is the Models sentence: top-level input is a string, a JSON object, or an array of text, and non-text is preprocessed into text or structured fields first. The object example is evidence that structured fields inside an object may hold records, not that images or binaries are legal.
- The 32k figure is not a cap on `state` alone. It is `state` plus the single longest question. The 64k figure is `state` plus every question.

### Gaps
- No opened page states a byte limit, a maximum JSON depth, or which JSON types are rejected inside an object (numbers are used in the example; binaries are excluded by the Models input row).
- No opened page says what the API returns when a request exceeds 64k or 32k tokens. Jaggedness only points at the Models page for the numbers.

## How should a question be written?

### Takeaway
Question ids stay in the harness. The model sees `instructions` and `criteria`, including backticked paths such as `` `ticket.messages[0].text` ``. Each question is one narrow judgment. Independent questions share one state and one request; a second request is only for a real data dependency. The model does not see another question's answer.

### Cited Findings
- Every question has an id, a `type` (`choice`, `score`, or `noul`), and `instructions`. Choice and Score also take `criteria`. Noul `criteria` is optional and clarifies yes and no. "Question IDs are for your code. They are not sent to the model. Write the complete question in `instructions`, even when the ID seems self-explanatory." — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), heading "Define a question" and the Tip under it.
- "Ask for one snap judgment per question." A good question is one "a knowledgeable person makes in a second." "Does this message convey urgency?" is given as good. "Analyze this message and determine the best course of action" is given as not good, because it needs slow reasoning and should be broken into small questions composed in code. If several factors matter, ask each separately and weight them in code. — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), heading "Ask for one snap judgment per question".
- "Every question in a request sees the same state, is evaluated independently, and returns a typed answer under the ID you chose." "Every answer is independent. One question's answer is not hidden context for another." Adding or removing a question does not change the others. The model returns a distribution over the options or levels supplied, "never a value outside them." — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), opening and heading "What comes back".
- "When a question is about one of those parts, name it in the `instructions` with a dot-and-index path to its key, including the backticks." The published examples are `` Does `ticket.messages[0].text` request a refund? `` and a second Noul that names `` `refund_policy` ``, `` `ticket.messages[0].text` ``, and `` `order.charges` ``. — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), heading "Reference specific fields".
- "Use a backticked dot-and-index path" such as `` `support.tickets[0].message` ``, and "include the backtick characters around each path inside the question." — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), step "Use structure in the input state".
- "Ask the most explicit, narrow, specific, atomic questions you can." The page calls this "probably the most important concept in this guide." The bad example is one Noul, "Is `message` spam?". The good example is six separate Nouls (credentials, unexpected reward, time pressure, sender mismatch, link-domain mismatch, disguised link). A second pair contrasts one Noul, "Is `trace.tool_calls` correct...", with nine field-level Nouls. — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), step "Decompose the questions".
- Send every question that uses the same state in one request. Questions run in parallel. "Questions in the same request are independent: one answer does not become context for another question." A second request is for when code cannot build it until it has the first answer: the answer is needed to fetch more data, to decide what the state is made of, or to pick the next question's options. "Otherwise, ask the questions together and combine their answers in code." "Two requests are the exception, not the rule." — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), headings "Ask multiple questions together" and "When one question depends on another".
- Choice: `instructions` is the question; `criteria` is a map of option name to description. "The model never sees the question id." "The option names and their descriptions are both sent to the model." Up to 255 options. Prefer the full list over a shortlist. Add `other` or `none of the above` when the list might not cover the input. `null` descriptions are used when the option name is clear on its own. — [Choice](https://docs.typesafe.ai/primitives/choice.md), headings "Request structure" and "Good practice: ask more than one question per call".
- Score: `criteria` is "an ordered array of level descriptions, from the low end of the scale to the high end. Should have at least two levels; the API accepts up to 10." "The model gets the descriptions and nothing else, and each level is judged on its own against the state." Level numbers are positions in that array, starting at 0. The question id "is not sent to the model." — [Score](https://docs.typesafe.ai/primitives/score.md), headings "Request structure" and "Levels".
- Noul: "Ask one yes/no question per Noul." Two conditions in one question ("angry and asking for a refund") make the value mean less; ask two Nouls and combine them in code. "Phrase the question so that a high value means yes." An inverted wording such as "Is the message free of personal data?" will be read backwards by later code. A statement is allowed. "Make the boundary between yes and no unambiguous." Add `criteria.true` and `criteria.false` when the boundary is subtle. Ids "are not sent to the model." — [Noul](https://docs.typesafe.ai/primitives/noul.md), headings "Request structure" and "Writing a Noul question".
- `instructions`, Choice option descriptions, Score level descriptions, and Noul `criteria.true` / `criteria.false` accept a string, an object, an array, or null. Use structure when a question has several parts, or when supporting data is already JSON. "The field names `question`, `focus`, `what`, `not_for`, and `examples` are not part of the API, and none are reserved." The model sees the names and the values. Use the same field names across Choice options. — [Advanced: structure](https://docs.typesafe.ai/primitives/advanced.md), headings "Where structure is allowed" and "When to structure a question"; [Choice](https://docs.typesafe.ai/primitives/choice.md), heading "Structured instructions and criteria".
- Keep questions short. A string is enough when the question is short and unambiguous. Put code-supplied data in its own field and refer to that field with backticks, rather than splicing it into a string. — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), step "Use structure in the questions".
- `jev-1.13` "answers the question you wrote, not the one you meant." "State the exact condition in the `instructions`." Put boundary cases in the criteria. Split unavoidable interpretation into two literal questions and combine them in code. Instructions with double negatives or "a property of a property" are less reliable; "identify the relevant parts of state by name." Contradictory instructions and criteria are a listed failure mode: "Align the criteria and instruction." Choice option order can change the answer: "Reorder the options and check the answer is consistent." — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), headings "Literal reading", "Indirection", "Contradictory instructions and criteria", and "Choice option order".
- Do not ask the model to do arithmetic, counting, or date comparison. "Jev is not a calculator." Count in code, or ask one question per candidate and add the answers in code. Dates are read as text; extract closed-set parts with Choice, including an explicit "not stated" option, and compare in code. "Please do not use score outputs ... to compute the exact magnitude of a number between two levels." — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), headings "Math and Numbers" and "Date and time comparison".
- `jev-1.13` "is not trained to generate text." Forcing generation by chaining Choices "will not work well." If the answer space is bounded, use a Choice over options. "If you really need to generate text... there are other models for that." — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), heading "Generation".
- Noul is not a scale of degree. "A Noul value of 0.5 means the model gives yes and no equal probability. It does not mean the candidate has a medium skill level." Measure a spectrum with a Score whose levels are written out. — [Primitives (Questions)](https://docs.typesafe.ai/primitives.md), heading "Choose a question type", and [Noul](https://docs.typesafe.ai/primitives/noul.md), heading "Reading a Noul".

### Inferences
- A harness that puts the real question only in the id, or that uses the id as a label the model is expected to understand, violates the published rule that ids are not sent.
- Paths must be written with backtick characters in the instruction string. A path without backticks is not what the pages specify.
- Speculative questions (a return reason asked even when the department may not be returns) are endorsed, because the harness ignores answers it does not need. That is still one judgment per question, not one question that branches.

### Gaps
- No opened page gives a character limit on `instructions` or on a single option description, separate from the 32k/64k token budgets on the Models page.
- No opened page says the model resolves a backticked path that does not exist in `state`, or a path written without backticks.

## What does confidence mean, and which page says it is not permission to act?

### Takeaway
Choice and Score `confidence` is a 0-to-1 summary of how peaked that answer's own probabilities are. It is not a second probability, and Noul does not have it. No opened page says the sentence "confidence is not permission to act and not proof the whole workflow is correct." The nearest published lines are: confidence 1.0 is not a guarantee the answer is correct; calibration is not a guarantee about any single answer; low confidence means do not act; and the harness, not the model, decides whether a given confidence is enough for a given action.

### Cited Findings
- Choice and Score answers include `probabilities`. "The shape of that distribution is what tells you how certain the model is." `confidence` "collapses that shape into a single number from 0 to 1." "It is 1 when all the probability is on one outcome and 0 when the probability is spread evenly. (Noul answers don't carry one.)" It "is a statistic computed from the probability distribution the answer already gives you." — [Confidence](https://docs.typesafe.ai/confidence.md), opening and heading "Confidence is derived from the probabilities".
- Choice formula, for `n` options and top probability `p_max`: `(p_max - 1/n) / (1 - 1/n)`. Only the top probability counts, so `(0.6, 0.3, 0.1)` and `(0.6, 0.2, 0.2)` both have confidence 0.4. Score confidence also counts distance from the peak level, and is floored at 0. "TypeSafe's `confidence` is one reasonable way to summarize a distribution, not the only one." The page also names top probability and the top-to-second ratio as measures the harness can compute itself. Top probability's meaning "depends on the number of options." — [Confidence](https://docs.typesafe.ai/confidence.md), heading "How confidence is calculated".
- Noul returns no `confidence`. "A value near 0.5 is the model saying it is unsure." If the harness wants a confidence-style number, the page gives `|2p - 1|`, which is 0 at `p = 0.5` and 1 at 0 or 1. That formula "is also the Choice formula ... applied to a yes-or-no Choice." — [Confidence](https://docs.typesafe.ai/confidence.md), heading "How confidence is calculated", subsection "Noul".
- "Low confidence: Do not act. Route to a human, request clarification, or fall back to a different system." Medium: "Proceed with caution" (confirm, flag, or gather more information). High: "Act automatically." "Where you draw those boundaries depends on the stakes." "A confidence threshold is not one number." "The correct threshold values depend on your domain and the performance of the model for your use case. Start with conservative thresholds, test with your own data, and adjust as you observe results." — [Confidence](https://docs.typesafe.ai/confidence.md), headings "Three paths for using confidence in your code" and "Thresholds scale with risk", including the Note.
- "In these examples, confidence 1.0 means the returned distribution puts all its probability on one level. This describes the model's answer, not a guarantee that the answer is correct." Different distributions can share one score; read `probabilities` and `confidence` with the score. — [Score](https://docs.typesafe.ai/primitives/score.md), heading "Reading a Score".
- "Calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct." System One "do[es] not write replies, produce code, or generate explanations of their reasoning." — [System One](https://docs.typesafe.ai/concepts/system-one.md), heading "How it differs from an LLM".
- "These rates describe groups of predictions, not a guarantee about any single answer. See Confidence for guidance on deciding when software should act or escalate." Higher probability "should correspond to a greater chance that the answer is correct," as a group property of calibration, not as a per-answer proof. — [AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer.md), heading "RLCD and calibrated decisions".
- "The answer tells you what; confidence tells you whether to act." The voice-banking example still splits the gate by action: below 0.6, or an `other` intent, goes to a person; `check_balance` at 0.6 proceeds; `approve_transfer` between 0.6 and 0.85 asks the user to confirm; only `approve_transfer` above 0.85 is treated as automatic in that example. — [Confidence-gated routing](https://docs.typesafe.ai/patterns/confidence-routing.md), the page description and heading "Example: voice banking commands".
- "Keep control flow, deterministic rules, and side effects in code." "Use probabilities and confidence to act, ask for review, or escalate." "Make code take different actions for confident and unconfident answers." The sample `if answer.confidence < 0.8` is inside that step's example, and the step says to test thresholds "by plotting confidence against accuracy on your data." — [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md), the summary Info and step "Route on uncertainty".
- "If you have tuned confidence thresholds against a specific version, pin that version's ID instead of the alias." `jev-latest` "can change without a change on your side." — [Models](https://docs.typesafe.ai/models.md), heading "Aliases".
- The agent-skill page's heading "You're using confidence thresholds everywhere" says: if the only goal is the best option, "choose the option with the highest confidence (rather than setting a confidence threshold)." If a specific statistical rule is wanted, "you should probably be using probabilities instead of confidence." — [Agent skill](https://docs.typesafe.ai/agent-skill.md), heading "Common issues".

### Inferences
- "Whether to act" on the routing page is a harness decision that reads confidence. It is not a claim that a high confidence value is itself permission. The same page withholds automatic action for the high-stakes option until a higher bar, and the Confidence page says the bar is the harness's and depends on stakes.
- Nothing opened says a high confidence on one question certifies the rest of the workflow. Independence is the opposite rule: each answer stands alone, and code composes them. A workflow-level proof is the harness's checks, which these pages place outside the model.
- The 0.5, 0.6, 0.8, 0.85, and 0.9 figures on the Confidence, Choice, Noul, how-to-build, and confidence-routing pages are scenario examples. The Confidence note forbids treating them as the correct values for every domain.

### Gaps
- No opened page contains the phrases "not permission to act" or "not proof the whole workflow is correct." The Score, System One, and AI primer lines above are the published denials of a correctness guarantee, and they are about one answer or about a group of predictions, not about a whole workflow.
- A search snippet from the function-calling cookbook described a composed call's confidence as the least certain part rather than proof that every part is right. That page was not opened, so it is not used here.

## What should the harness do on low confidence, a Noul near one half, a missing answer, or an HTTP failure?

### Takeaway
Low Choice or Score confidence: do not act on that answer; route to a person, ask for clarification, or fall back. A Noul near one half is the same kind of uncertainty and has no separate confidence; the pages say middle values can go to a person, and the cutoffs are the harness's. A missing field in a successful body is a response-validation error in the Python SDK; the docs do not say to retry it or to treat it as low confidence. For HTTP, the API page says to back off and retry 429 and 529, and it does not say to retry 401 or 422.

### Cited Findings
- Low confidence: "Do not act. Route to a human, request clarification, or fall back to a different system. The model is telling you it does not have enough information or the question is not a good fit." Medium confidence is caution, not a silent proceed. "The correct threshold values depend on your domain." — [Confidence](https://docs.typesafe.ai/confidence.md), headings "Three paths for using confidence in your code" and "Thresholds scale with risk".
- The Choice triage example treats `department.confidence < 0.3` as "Not clear which team to send to. Let a person decide," and `requested_resolution.confidence < 0.5` as "Ask, don't guess." Those comparisons are inside that example. — [Choice](https://docs.typesafe.ai/primitives/choice.md), heading "A more complex example".
- "A value near 0.5 means the model gives yes and no similar probability." "There is no separate `confidence` value for a Noul." "Where to set the threshold depends on the cost of being wrong. Use 0.5 when yes and no are equally easy to act on. Raise it when acting on a false yes is expensive, such as paging someone or issuing a refund. Lower it when missing a true yes is expensive, such as failing to flag a safety issue. Values in the middle can go to a person rather than either code path." — [Noul](https://docs.typesafe.ai/primitives/noul.md), heading "Reading a Noul".
- The Noul routing example sets `YES = 0.8` and `NO = 0.2`, and sends the message to review when either Noul is strictly between them. "The thresholds live in your code. If reviewers see too many messages, narrow the gap between `NO` and `YES`. If too many wrong routes get through, widen it." — [Noul](https://docs.typesafe.ai/primitives/noul.md), heading "Handling multiple Noul answers in code".
- On the Confidence page, distance from 0.5 is the optional confidence-style number for a Noul, and it is 0 at one half. — [Confidence](https://docs.typesafe.ai/confidence.md), subsection "Noul".
- The `jev-1.13` counting sample uses `YES = 0.5` with the comment "up to you on what you want the threshold to be, depends on your usecase." — [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md), heading "Math and Numbers".
- A normal response has "one entry in `answers` per question, under the ids from the request." — [Choice](https://docs.typesafe.ai/primitives/choice.md), heading "Response structure". The same shape is described for Noul and Score.
- Python SDK `TypeSafeAPIResponseValidationError`: "A successful HTTP response whose body was missing or structurally invalid required data." `field_path` is "Dotted path to the offending field, such as `answers.tone.confidence`." — [Exceptions](https://docs.typesafe.ai/sdk/python/api/exceptions.md), heading "Response validation".
- HTTP errors on the API page:

  | Status | What the page says |
  | --- | --- |
  | `401 Unauthorized` | "Missing or invalid API key. Check the `Authorization` header." |
  | `422 Unprocessable Entity` | "The request body failed validation — for example a missing required field or a malformed question. The body details the offending field." |
  | `429 Too Many Requests` | "You have exceeded your rate limit. Back off and retry after a short delay." |
  | `529 Overloaded` | "TypeSafe is temporarily overloaded. Retry after a short delay." |

  "When you receive a `429 Too Many Requests` or `529 Overloaded` response, retry the request with exponential backoff instead of retrying immediately. Our client SDKs handle this automatically, so no extra handling is needed if you use one of our SDKs with its default retry policy." — [API reference](https://docs.typesafe.ai/api.md), headings "Errors" and "Handling rate limits".
- The API Errors table, as opened, does not list 400, 403, 404, or 5xx, and it does not say to retry 401 or 422. The Python exceptions page does name those cases: `TypeSafeBadRequestError` (400), `TypeSafeAuthenticationError` (401), `TypeSafePermissionDeniedError` (403), `TypeSafeNotFoundError` (404), `TypeSafeUnprocessableEntityError` (422), `TypeSafeRateLimitError` (429, with `retry_after_ms` or `None`), `TypeSafeInternalServerError` ("The server failed to process the request (5xx)"), `TypeSafeAPIConnectionError` ("A request failed without an HTTP response"), and `TypeSafeAPITimeoutError` ("A request exceeded its configured timeout"). — [Exceptions](https://docs.typesafe.ai/sdk/python/api/exceptions.md), headings "HTTP errors" and "Connection errors".
- `RetryPolicy` is configurable: `max_retries` ("Maximum retries after the initial attempt; `0` disables retries"), exponential `backoff_initial` doubled up to `backoff_max`, `http_statuses` ("HTTP status codes that are retried"), `respect_retry_after`, `api_connection_error`, `api_timeout_error`, plus an optional predicate. The page's example constructs `RetryPolicy(max_retries=3, timeout=10.0, http_statuses={429, 500, 502, 503, 504})`. A `timeout` on the policy is "Total retry budget in seconds per SDK call"; the client "Stops before a retry whose delay would reach or exceed the budget, re-raising the last error." — [Retries](https://docs.typesafe.ai/sdk/python/api/retries.md), heading "typesafe_sdk.RetryPolicy".
- Models: SDKs "retry with backoff by default and honor the `retry-after` header when the response carries one." Direct HTTP callers are pointed at "Handling rate limits." — [Models](https://docs.typesafe.ai/models.md), the rate-limits bullet under "Current models".

### Inferences
- A Noul of 0.5 is not a middle score on the thing asked. The Noul page says it is equal probability of yes and no, and the primitives page says it is not a medium degree. Sending it to a person is the published middle path, not a requirement to treat 0.5 as true or false.
- The 0.8/0.2 band and the 0.5 counting cutoff are examples with explicit "your code" / "up to you" wording. They are not a default band for every harness.
- The retry example's status set `{429, 500, 502, 503, 504}` does not include 529, while the API page names 529 as a retry. Those are two pages, not one default policy. A harness on raw HTTP has a written rule only for 429 and 529.

### Gaps
- The docs do not say what a harness should do when a successful JSON body omits an answer, beyond the Python SDK raising `TypeSafeAPIResponseValidationError`. They do not say to retry that error, to substitute a probability, or to treat the gap as low confidence.
- The Retries page excerpt does not state the default `max_retries`, the default `http_statuses`, or the default values of `api_connection_error` and `api_timeout_error`. The sample `max_retries=3` is an example in the constructor, not a labeled default.
- The API Errors section does not say what to do on a connection failure, a timeout, or a 5xx other than the separate 529 row. The exceptions page names the types and does not add a recovery policy.
- No opened page says to re-ask the same question when confidence is low or a Noul is near one half. The published actions are to change the harness's behavior (review, clarify, fall back), not to repeat the call.

## Can the harness ask JEV to evaluate or run a program?

### Takeaway
No opened page says JEV can run a program. The pages say it evaluates text state and returns a typed judgment, and that it does not generate code, call tools, edit files, or choose its next action. Asking it to judge program text is not described as execution. `jev-1.13` is a poor fit for assembly or binary, and arithmetic about a program belongs in code.

### Inferences
- "Evaluate" in these docs means answer typed questions about text state. A harness can place source text in `state` under the ordinary text rule. That is not a published ability to execute the program, and no page says the judgment is a substitute for running it.
- Binary or bytecode is in the "pre-process into text" bucket on the Models page, and jaggedness says binary-encoded instructions are a weak case for `jev-1.13`. The docs do not say a base64 blob is a legal state.

### Gaps
- No opened page says "you may ask JEV to evaluate a program" or "you may not put source code in state." The programming-language sentence on the jaggedness page assumes questions about languages are asked; it does not define a program-evaluation product.
- No opened page describes a code-execution tool, a sandbox, or a way for the model to return stdout.
