## Every classify call: model, question, and what the answer changes

### Takeaway
At this commit the product has two classify surfaces and one opted-in caller. `models.classify` is a codemode global whose model id and questions are chosen by the script. `ctx.modelRegistry.classify` is the same operation for extensions. The only extension that calls it is the example `jev-router.ts`, and it asks `typesafe/jev-latest` one `choice` question to pick the planning chat model. The default agent loop does not call JEV.

### Cited Findings
- Codemode is off unless an MCP server turns it on or settings add it. Classifier models are not in `/model`. Scripts reach them only through `models.classify`. Extensions reach them through `ctx.modelRegistry.classify()` without codemode. — [packages/coding-agent/docs/models.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/models.md) (blob `af3fb7e8a0a47651d21e2fd88a7d79cfb6865083`), section "Use classifier models".
- Built-in Jev ids in that same section: `typesafe` / `jev-latest` (`TYPESAFE_API_KEY`); `openrouter` / `typesafe/jev-1.13` and `~typesafe/jev-latest`; `cloudflare-workers-ai` / `typesafe/jev` (also Clef and Clef Flash, which are not Jev); `vercel-ai-gateway` / `typesafe-ai/jev`; `opencode` / `jev-1.13` and `jev-1.13-free`. Chat models on a llama.cpp router are also listed as classifiers. — same file.
- `models.classify` is bound in `createModelGlobals` in [packages/coding-agent/src/extensions/codemode/execute.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/extensions/codemode/execute.ts) (blob `3d7bdf66ee4fb89d64e09e08ac0b1d4b4bba7a79`). The script passes the model and the context. The harness resolves the model by `provider` and `id` only, checks the context shape, then calls `models.classify(resolved, context, { signal })`. A script-supplied `baseUrl` or `headers` is not used for the request. There is no harness-chosen model id or question on this path.
- The public question types, from the codemode docs, are `choice` (label to meaning), `score` (ordered level strings), and `bool` (`criteria.true` / `criteria.false`). One call answers every question in `context.questions`. — [packages/coding-agent/docs/codemode.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/codemode.md) (blob `08136c00a8db439a480134c8d7b05693d724e975`), "Classify". The TypeSafe wire maps public `bool` to `noul`. — [packages/ai/src/api/typesafe-system-one.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/api/typesafe-system-one.ts) header comment, and `parseAnswers` in [packages/ai/src/api/system-one-shared.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/api/system-one-shared.ts), which requires `answer.type === "noul"` for a bool.
- The docs example, not a runtime call, uses `typesafe` / `jev-latest` with one `bool` ("Does the user approve of the result?") and returns `result.answers`. — models.md, the script under "Use classifier models". A second docs example uses the same model with a `choice` named `sentiment` (positive / negative / neutral) and a `score` named `urgency` (three levels), one `classify` per message inside `Promise.all`, and returns `{ message, sentiment, urgency }` or `{ message, error }`. — codemode.md, "Classify several items".
- The only `ctx.modelRegistry.classify` call in product code is [packages/coding-agent/examples/extensions/jev-router.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/examples/extensions/jev-router.ts) (blob `78130dd1c42f3897da0e1814db1c856071d097df`). It is an example: `pi -e ./jev-router.ts --model jev/auto`. It looks up `findOfType("classifier", "typesafe", "jev-latest")`. State is `{ prompt }` where `prompt` is the last user message's text, non-text blocks dropped, cut with `.slice(0, 16_000)`. The only question is `complexity`, type `choice`, instructions "How demanding is the software engineering work requested in `prompt`?", criteria `standard` ("Ordinary features, fixes, reviews, or questions") and `complex` ("Subtle design, cross-cutting changes, or hard debugging").
- What that answer changes, in the same file: if `stopReason === "stop"`, the answer is a `choice`, and `(answer.probabilities.complex ?? 0) >= 0.5`, the planning model is `openai-codex` / `gpt-5.6-sol`. Otherwise it is `openai-codex` / `gpt-5.6-terra`. The `0.5` comparison is this example's. No other file in the searches applies a numeric Jev threshold. After the first successful `edit` or `write` in the turn, later requests go to `openai-codex` / `gpt-5.6-luna` with no further classify. `request.reason === "direct"` (the file names compaction summaries) goes to Luna with no classify. If the previous model is already Sol or Terra, classify is skipped and that id is kept.
- `modelRegistry.classify` is a pass-through to `runtime.classify`. Comment on the registry method: "Classify structured state with request-time authentication. Never rejects." — [packages/coding-agent/src/core/model-registry.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/core/model-registry.ts) (blob `ffd31756416c38eec8eb1b994618f9ebced4ec57`), `findOfType` and `classify`. Docs say a router call "adds latency before the first token of the turn." — [packages/coding-agent/docs/virtual-models.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/virtual-models.md).
- The post's worked script is not a file in the repo. It calls `models.getModelOfType("classifier", "cloudflare-workers-ai", "typesafe/jev")` with one `choice`, `frustration`, criteria `none` / `mild` / `high`, instructions to judge only emotional tone. Four async workers pull Linear issues. The script scores `probabilities.mild * 0.5 + probabilities.high` in JavaScript, returns `{ total, counts, flagged titles }`, and `store("frustration", results)`. The chat reply in the post then summarizes that return value. — [the post](https://earendil.com/posts/you-said-no-mcp/).
- GitHub code search for `modelRegistry.classify` in `earendil-works/pi` at this ref returned four files: `llama-cpp.md`, `models.md`, `virtual-models.md`, and `jev-router.ts`. Search for `models.classify` returned docs, the binding in `execute.ts`, package READMEs, changelogs, and tests. No other product caller hardcodes a Jev model id.

### Inferences
- A harness copying Pi does not put Jev in the chat model picker and does not hardcode questions inside the codemode binding. The script owns the questions. The one shipped judgment (complex vs standard, Pi's `0.5` on `probabilities.complex`) lives in an example router, runs before the first token, and is not repeated after the route is chosen.
- Jev is not asked to plan, to edit, to pick Luna, to score later turns, or to choose tools. Those are ordinary code in `jev-router.ts` or BM25 (next sections). Chat models "are listed but cannot be run from scripts." — codemode.md, "Models".

## What the harness keeps out of the chat model's context

### Takeaway
Nested `models.classify` results stay inside the QuickJS script. The chat model is shown the codemode tool's `content`: a status header plus what the script passed to `text()`, `console.*`, `image()`, or a top-level `return`. The full answers are not copied into that content unless the script puts them there.

### Cited Findings
- "Nested tool calls never enter the LLM context; only the script's output and return value do." — [packages/codemode/README.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/codemode/README.md) (blob `d2878650eb6d4384eff90992749191b5896145e4`), first paragraph.
- "Only the script's output reaches the model, so a script can run calls in parallel and filter large results before the model sees them." — codemode.md, opening paragraph. A top-level `return` "adds the value like `text()`." The tool result the runtime builds starts with `Script completed` or `Script failed`, the wall time, and `Output:`, then those items. — same doc, "Scripts" and "Globals"; matching code in `executeCodemode`: on success, `result.value` is appended as text, then `content` is the header plus truncated items. — execute.ts around the `pi extension: a returned value is appended like text()` comment.
- The nested-call row for `models.classify` stores `args` as `` `${provider}/${id}` `` only. The comment on `createModelGlobals` says rows "show only the model, never prompts or image data." The row also stores status, duration, an error preview of at most 500 characters (`ERROR_PREVIEW_CHARS`), and cost. It does not store `answers`. — execute.ts, `runModelCall`.
- `ToolResultMessage.nestedCalls` is "Kept for the session record; not sent to the model." `NestedToolCalls` says "Results are not recorded." — [packages/ai/src/types.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/types.ts) (blob `0358843d1b3b1b976d6b385259032ca5b1e8fc20`). The recorder copies arguments, name, status, duration, and a 500-character error, and drops results. Comment: "Nested results are not persisted." Limits: `NESTED_CALL_LIMITS` `maxCalls: 256`, `maxArgumentBytesPerCall: 8 * 1024`, `maxArgumentBytesTotal: 32 * 1024`, `maxErrorChars: 500`. — [packages/coding-agent/src/core/nested-tool-calls.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/core/nested-tool-calls.ts) (blob `b014dc0daef7b5154e6e814b3ac2ff95b0930557`).
- A code search for `toolResult.details`, `msg.details`, and `result.details` under `packages/ai/src` returned no matches. `nestedCalls` appears in `packages/ai` only on that type comment. Provider serializers in that package therefore do not read those fields. `details` is still stored on the tool result for the UI. — types.ts; execute.ts return value `{ content, details }`.
- `usage` on a tool result "is not part of the main model-call usage" and is "Not part of main LLM context accounting." Classifier token counts are still added onto the codemode tool result so the footer and `/session` can show cost. `jev-latest` on the direct TypeSafe provider "report[s] tokens at no cost" because it has no catalog price. — types.ts; models.md, "Use classifier models".
- `store(key, value)` keeps JSON on a `codemode-store` custom session entry, only if the script succeeds. It is not model context until a later script `load`s it and emits it. Caps in the docs: one value at most 262144 characters of JSON, all values together at most 1048576. — codemode.md, "Store values". The post uses this: verdicts stored under `frustration`, return value is counts plus titles, and the reply says the verdicts can be read later without fetching the issues again. — [the post](https://earendil.com/posts/you-said-no-mcp/).
- Output that does go to the model is capped. Default `max_output_tokens` is 10000 (estimated at 4 characters per token). Longer output keeps its start and end; the full text is spilled to a temp file. A script fails past 16777216 characters of text and base64 image data, or past 100000 `text()`, `image()`, and `console` calls. — codemode.md, "Scripts".
- The router never puts the classify result into the chat transcript. It only returns a `ModelRoute` (`model`, `thinkingLevel`, `state`). The phase is router state on the session branch. — jev-router.ts; virtual-models.md says the transcript records the selection and each dispatched model.

### Inferences
- Copying Pi means: run Jev inside the sandbox, let the script reduce, and treat `text`/`return` as the only model-visible channel. Do not append `answers` in the harness. The UI and the session may still show that a classify happened (`provider/id`, status, duration, cost) without the state or the probabilities.
- If a script returns the raw `answers`, those probabilities do enter the chat context, bounded by the output cap. The harness does not strip them. The practice is the script's return shape, as in the post (counts and titles) and the docs example (choice and score, not the whole probability map).

### Gaps
- I did not line-read every provider's message converter. The negative claim (details and nestedCalls are not sent) rests on the type comment plus a code search of `packages/ai/src` with no reads. A converter outside that tree could still stringify a whole message; I did not find one.
- I did not measure token counts for the "Script completed" header. It is part of `content`, so it does enter the chat context.

## On provider failure, does classify throw? What if Jev is missing?

### Takeaway
Provider failure does not reject `classify`. The result has `stopReason` `"error"` or `"aborted"` and an `errorMessage`. The example router, if `jev-latest` is absent or the call did not stop cleanly, plans on Terra and does not throw.

### Cited Findings
- `classifySystemOne` catches provider failures and returns the result. On HTTP failure it throws inside its own `try` (`if (!next.ok) throw httpError(...)`), retries with `options.maxRetries ?? 2`, and in the `catch` sets `stopReason` to `"aborted"` if the caller's signal aborted, otherwise `"error"`, plus `errorMessage`. Missing API key (`No API key for provider`) and a malformed answer body take the same path. A billed response with a bad body still attaches `usage` before parsing. — [packages/ai/src/api/system-one-shared.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/api/system-one-shared.ts), `classifySystemOne`.
- `Models.classify` is documented "Never rejects." Its `try` delegates to `provider.classify`; the `catch` returns `classifierErrorResult`. — [packages/ai/src/models.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/models.ts) (blob `d8693c978c0f424808f70647f97f92fef6617e7d`), `async classify`. `ModelRuntime.classify` does the same. — [packages/coding-agent/src/core/model-runtime.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/core/model-runtime.ts) (blob `7edd44048de0bf29a0d949a4545c85c8539ee495`). `classifierErrorResult` sets `answers: {}`, `stopReason` `"aborted"` or `"error"`, and `errorMessage` from the error. — [packages/ai/src/utils/model-operations.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/ai/src/utils/model-operations.ts).
- The codemode docs say `classify()` and `generateImages()` "do not throw on provider errors: check `stopReason` and `errorMessage`." — codemode.md. `runModelCall` returns that result to the script even when `stopReason !== "stop"`. It marks the nested row `"error"` or `"cancelled"`. It does not throw. — execute.ts.
- The script does throw before any provider call if the context shape is wrong (`checkClassifierContext`), if the model argument is not `{ provider, id }`, or if that pair is not a classifier. Those throws fail the script unless the script catches them. — execute.ts, `runModelCall` and `checkClassifierContext`.
- If Jev is missing: `findOfType` returns `undefined` when `getModelOfType` misses. It does not check credentials. — model-registry.ts, `findOfType`. The router then `if (!jev) return TERRA` and does not call `classify`. — jev-router.ts. If the model exists but classify does not stop (`stopReason !== "stop"`), `answer` is `undefined` and the same function returns Terra. A complex probability below `0.5`, or a missing `probabilities.complex` (treated as `0`), also returns Terra. Terra is `openai-codex` / `gpt-5.6-terra`.
- The router does throw if the chosen OpenAI Codex id is not in the catalog (`Model ${PROVIDER}/${id} is not in the catalog`). That throw is not the Jev failure path. — `routeTo` in jev-router.ts.
- The file header says the example "Requires TypeSafe credentials (TYPESAFE_API_KEY) and an OpenAI Codex login." A missing key is still a failed classify, which the function maps to Terra, not a throw. — jev-router.ts; system-one-shared.ts.

### Inferences
- The practice to copy is: classify returns a tagged error result; the caller branches on `stopReason`. The example router's branch on failure and on a missing model is the same branch as "not complex": the cheaper planning model. It does not tell the chat model that Jev failed.
- Do not treat "classify never throws" as "the script never throws." A bad question object throws inside the sandbox, before the provider, and that can fail the whole codemode tool (`isError: true`, `Script failed`).

### Gaps
- I did not open `retryProviderRequest`, so I cannot say which HTTP statuses are retried, only that the default retry count is 2 and that the final failure is an error result.
- I did not confirm, by running it, that a missing `TYPESAFE_API_KEY` leaves `jev-latest` in the catalog. The code path above is what the source does if `findOfType` returns the model and the request then has no key.

## Is there a concurrency cap on classify?

### Takeaway
Yes. One codemode script may have at most four `models.classify` and `models.generateImages` calls in flight. The constant is `MAX_CONCURRENT_MODEL_CALLS`. Further calls wait. This cap is Pi's, in this file, and it is shared with image generation.

### Cited Findings
- `const MAX_CONCURRENT_MODEL_CALLS = 4` with the comment "`models.classify()` and `models.generateImages()` calls one script may have in flight; `Promise.all` over many items queues the rest." `createModelGlobals` wraps both operations in `createLimiter(MAX_CONCURRENT_MODEL_CALLS)`. The limiter runs at most `limit` calls at once, in call order. — execute.ts, lines at the constant and `runModelCall`'s `await limit(() => run(...))`.
- The docs state the same rule in prose: "At most four such calls run at once per script; more calls wait for a free slot, so `Promise.all()` over many items is fine." — codemode.md, paragraph after the `models` type block.
- The post's script starts four workers with `Promise.all([worker(), worker(), worker(), worker()])`. That is the example script's own pool, in the post, not a second constant in the repo. — [the post](https://earendil.com/posts/you-said-no-mcp/).
- `jev-router.ts` makes one classify call. It is not under `MAX_CONCURRENT_MODEL_CALLS`. I found no other cap on `modelRegistry.classify`.

### Inferences
- A script may still fan out with `Promise.all`. The harness queues past four. The post's four workers match the cap; they do not define it. Image calls consume the same four slots.

### Gaps
- I did not look for a process-wide cap across scripts or sessions. The constant is per `createModelGlobals` call, and `executeCodemode` builds that once per script.

## Does this harness use JEV to choose the tool list?

### Takeaway
No. Tool discovery is BM25, shared by `searchTools` inside codemode and the `tool_search` tool for deferred tools. It does not call `classify`. Jev is a separate, optional call the script makes after it has already chosen tools.

### Cited Findings
- [packages/coding-agent/src/extensions/tool-search/tool.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/extensions/tool-search/tool.ts) (blob `85b29a4cdb9eba68fffd306a9246f7577ae5bd7a`) opens: "Tool discovery: a BM25 ranker over tool metadata, shared by `searchTools()` in codemode scripts and the optional `tool_search` tool." `tool_search` "searches tools that are not declared to the model (`codemode` and `deferred` exposure) and loads the matches, so they are declared for the next model call." `DEFAULT_TOOL_SEARCH_LIMIT = 8`. `Bm25Ranker` is Okapi BM25 with default `k1` 1.2 and `b` 0.75. The tool's own exposure is `"model-only"`. Its description says it searches deferred tool metadata with BM25. The file has no `classify` call.
- `searchTools` in execute.ts builds a `Bm25Ranker` and ranks `createToolSearchDocument` rows. Default limit is `DEFAULT_TOOL_SEARCH_LIMIT`. The docs say it "Rank[s] callable tools by relevance (BM25, default limit 8)." — execute.ts, `createDiscoveryGlobals`; codemode.md globals table.
- MCP exposure `codemode` (the default) means tools are callable from scripts but neither declared to the model nor listed in the codemode description; scripts find them with `searchTools()`. Exposure `deferred` means not declared until `tool_search` loads them, and "Does not need codemode." — [packages/coding-agent/docs/mcp.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/mcp.md), and the comment block in [packages/coding-agent/src/core/mcp-servers.ts](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/src/core/mcp-servers.ts) from the code search fragment. `codemode.inlineBudget` defaults to 3000 estimated tokens; tools that do not fit are left out and found with `searchTools()`. — [packages/coding-agent/docs/settings.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/settings.md), from the search fragment.
- The post says tools should be "discoverable by their documentation and description" and shows a script that calls Linear MCP tools and then `models.classify`. Discovery and classification are sequential steps in that script, not one Jev decision. — [the post](https://earendil.com/posts/you-said-no-mcp/).
- `tool_search` is off unless enabled with `defaultTools` or `--tools`. — [packages/coding-agent/docs/cli.md](https://github.com/earendil-works/pi/blob/83692682f095528f8b71652ddacff7075e36e893/packages/coding-agent/docs/cli.md), "Tool search", from the search fragment.

### Inferences
- Copying Pi means leaving the tool list to BM25 over names, descriptions, parameter schemas, and namespace text, with deferred declaration. Jev is used on the data those tools return, inside the script, and only if the script asks. The example router does not consult Jev about tools either.

### Gaps
- A second public coding-agent skill, [FrancoisChastel/jev-code `skills/jev/SKILL.md`](https://github.com/FrancoisChastel/jev-code/blob/main/skills/jev/SKILL.md), advertises `jev_classify` and related tools for coding agents. I did not open its call path, so no practice here is taken from it.
- I did not read the BM25 tokenization or the `isSearchable` exposure filter line by line. The ranker class and the "no classify" fact are from the file header, the class, and the absence of `classify` in that file's search hits.
