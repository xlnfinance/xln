# MCP dynamic tool discovery implementations

Scope is implementations of either (1) SEP-1821 `ServerCapabilities.tools.filtering` plus a `query` argument on `tools/list`, or (2) a server that starts with a small tool list and adds or removes tools at runtime under a documented dynamic-toolset flag. Ordinary static tool registration is not treated as this feature. Pages were opened on 2026-10-03.

## Which repos implement SEP-1821 `tools.filtering`, or a documented dynamic-toolset flag?

### Takeaway
SEP-1821 never landed: the spec PR and issue were closed unmerged, and a code search of `org:modelcontextprotocol` for `tools.filtering` returned nothing. The well-known dynamic-toolset flag is GitHub's local-only `--dynamic-toolsets` / `GITHUB_DYNAMIC_TOOLSETS`, and that flag was deleted from `github/github-mcp-server` main on 2026-05-20. The SDK issue titled "Support for dynamic tools" is an open C# feature request, not a `tools/list` query implementation.

### Cited Findings
- SEP-1821 ("Dynamic Tool Discovery", author Egor Orlov / @truehazker, created 2025-11-17) proposes an optional `query` string on `ListToolsRequestParams` and `ServerCapabilities.tools.filtering`. Present means the server processes `query`; absent means `query` is ignored and all tools are returned. Status in the issue text is Draft, sponsor "None (seeking sponsor)". The issue is closed. — [Issue #1821](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1821)
- The schema PR for that SEP, [PR #1822](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1822), adds `ServerCapabilities.tools.filtering` and a `query` parameter on `tools/list`. It was closed, not merged, on 2026-06-13 by @localden: "Closing this proposal as it has not received a sponsor and there is an active recommendation to engage in Discord." It was removed from the SEP Review Pipeline on 2026-08-23. — [PR #1822](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1822)
- GitHub code search `tools.filtering org:modelcontextprotocol` returned `total_count: 0` on 2026-10-03. The same search for `GITHUB_DYNAMIC_TOOLSETS repo:github/github-mcp-server` also returned 0, which matches removal from current main (below), not a search outage by itself. — GitHub code search via the GitHub MCP `search_code` tool, 2026-10-03
- A later spec draft, SEP-2636, says it removed its own `query` parameter because that surface is "SEP-1821's territory", and lists SEP-1821 as orthogonal. That draft does not implement `tools.filtering`. — [PR #2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636)
- GitHub MCP server dynamic mode, documented on tag `v0.30.1`, is local/stdio only. Flags are `--dynamic-toolsets` and env `GITHUB_DYNAMIC_TOOLSETS`. Remote server column says "Not available". It "Starts with only discovery tools (`enable_toolset`, `list_available_toolsets`, `get_toolset_tools`), then expands on demand." If `--tools` is also set, the server starts with those three plus the named tools. — [server-configuration.md at v0.30.1](https://github.com/github/github-mcp-server/blob/v0.30.1/docs/server-configuration.md)

That count does not match the three discovery tools named in the v0.30.1 doc. — [Issue #275](https://github.com/github/github-mcp-server/issues/275); contradicted on the tool count by [v0.30.1 server-configuration.md](https://github.com/github/github-mcp-server/blob/v0.30.1/docs/server-configuration.md)
- On tag `v0.31.0`, `EnableToolset` in `pkg/github/dynamic_tools.go` looks up the toolset, calls `deps.Inventory.EnableToolset(toolsetID)`, then `st.RegisterFunc(deps.Server, deps.ToolDeps)` for each tool in the toolset. GitHub's PR #2512 text does not say that. — [nulab commit 06fb2c0](https://github.com/nulab/backlog-mcp-server/commit/06fb2c0bb6578cb2102db29cfd407788ae9a8cba); [PR #2512](https://github.com/github/github-mcp-server/pull/2512)

### Inferences
- As of 2026-10-03 there is no standards-track implementation of SEP-1821 to point a client at. Dynamic toolset behavior that did ship is a server-local convention (meta-tools plus mutating the registered tool list), and the reference server people cite for it has since deleted the flag.
- Hermes PR #3812 (next section) names `GITHUB_DYNAMIC_TOOLSETS=1` as the example server. That example matches the server as of the PR (merged 2026-03-29) and does not match `github/github-mcp-server` main after 2026-05-20.

## For each hit, does the code send `notifications/tools/list_changed`, and which client sees the new tool without reconnecting?

### Takeaway
The protocol notification is real and older than SEP-1821. Official Go SDK `Server.AddTool` sends `notifications/tools/list_changed` when list-changed is enabled (the default). GitHub's removed dynamic mode reached that path through `RegisterFunc` → `AddTool`, so a client that handles the notification could see the new tools without reconnecting. Zed and Hermes are the clients whose docs or merged PRs say they reload on that notification. On protocol `2026-07-28`, the Go SDK only delivers the notification to sessions that opted in with `subscriptions/listen`.

### Cited Findings
- Spec `2025-06-18`: servers that support tools declare `capabilities.tools.listChanged`. When the list changes, a server that declared `listChanged` SHOULD send `{"method":"notifications/tools/list_changed"}`. The `tools/list` request example has `cursor` only, no `query`. — [tools.mdx 2025-06-18](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/server/tools.mdx)
- Spec `2026-07-28`: `listChanged` still means the server will emit notifications when the tool list changes. The set MAY change over time, but "MUST NOT vary per-connection or as a side effect of other requests on the connection." The notification SHOULD go to clients that opened a `subscriptions/listen` stream with `toolsListChanged: true`. The same page still shows the method name `notifications/tools/list_changed`. — [tools.mdx 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)
- `modelcontextprotocol/go-sdk` `mcp/server.go` on main: `(*Server).AddTool` calls `s.changeAndNotify(notificationToolListChanged, ...)`. `RemoveTools` uses the same notification. If the user did not set capabilities, tools are advertised as `&ToolCapabilities{ListChanged: true}`. `shouldSendListChangedNotification` returns true for tool-list changes when `caps` or `caps.Tools` is nil, otherwise `caps.Tools.ListChanged`. — [server.go](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/refs/heads/main/mcp/server.go)
- The constant is `notificationToolListChanged = "notifications/tools/list_changed"` in `mcp/protocol.go`. — [protocol.go](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/refs/heads/main/mcp/protocol.go)
- `notifySessions` in that same `server.go`: legacy sessions (initialize params nil, or `ProtocolVersion < protocolVersion20260728`) receive the notification on the shared session channel with no opt-in. Sessions on the new protocol receive it only if they have an active `subscriptions/listen` stream that opted into that notification type (`s.toolChangeSubscriptions`). Comment cites SEP-2575. Notifications are debounced by `notificationDelay` (10ms) via `time.AfterFunc`. — [server.go `notifySessions`](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/refs/heads/main/mcp/server.go)
- GitHub dynamic mode at `v0.31.0` does not call the notification itself. `enable_toolset` registers each newly enabled tool with `RegisterFunc`, and `RegisterFunc` calls `s.AddTool`. On the official Go SDK above, `AddTool` is what emits `notifications/tools/list_changed`. A client can then see the new tool without a new connection only if it receives that notification and calls `tools/list` again. The GitHub docs do not name such a client. — [dynamic_tools.go at v0.31.0](https://raw.githubusercontent.com/github/github-mcp-server/v0.31.0/pkg/github/dynamic_tools.go); [server_tool.go at v0.31.0](https://raw.githubusercontent.com/github/github-mcp-server/v0.31.0/pkg/inventory/server_tool.go); [go-sdk server.go](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/refs/heads/main/mcp/server.go)
- `mark3labs/mcp-go` `(*MCPServer).AddTool` (and add-tools / delete paths) sends `mcp.MethodNotificationToolsListChanged` to all initialized sessions when `s.capabilities.tools.listChanged` is set. The comment quotes the spec SHOULD. This is SDK plumbing, not a dynamic-toolset product flag. — [mcp-go server.go](https://raw.githubusercontent.com/mark3labs/mcp-go/main/server/server.go)
- Zed: [PR #42453](https://github.com/zed-industries/zed/pull/42453) merged 2025-12-16 (commit `eba811a` into main). On `notifications/tools/list_changed`, `ContextServerRegistry` runs `reload_tools_for_server`. Release notes: "MCP tools are now automatically reloaded when a context server sends a tools/list_changed notification, eliminating the need to restart the server to discover new tools." — [PR #42453](https://github.com/zed-industries/zed/pull/42453); [Zed preview 0.211.3 notes](https://zed.dev/releases/preview/0.211.3)
- Hermes agent reloads without restart or `/mcp refresh`. Detail is in the next section. — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)
- FastMCP's client docs show a `MessageHandler.on_tool_list_changed` callback. The worked example clears `cached_tools` so the next access refetches. The library does not, on that page, push the new tools into a model by itself. — [FastMCP notifications](https://gofastmcp.com/clients/notifications)
- C# SDK issue #1239 (2026-02-03) reports that a client handler registered for `notifications/tools/list_changed` (via `McpClientOptions.Handlers.NotificationHandlers` or `McpSession.RegisterNotificationHandler`) stops being invoked about 2–3 minutes after connect on Streamable HTTP, unless a debugger is attached. The reporter says MCP Inspector, connected at the same time, keeps receiving the notifications. So the SDK can observe the notification, and this bug says a long-lived HTTP client may stop seeing later changes. — [Issue #1239](https://github.com/modelcontextprotocol/csharp-sdk/issues/1239)
- `dmcp` documents that search results become callable after `notifications/tools/list_changed`. It does not name a host that consumes the notification. — [dmcp README](https://github.com/Grep-Juub/dmcp)
- `agent-discover` documents that activate/deactivate emits `tools/list_changed` and that activated servers are usable without restarting the host. — [agent-discover README](https://github.com/keshrath/agent-discover)
- OpenCode PR #5913 proposes subscribing to `notifications/tools/list_changed` and publishing an internal `mcp.tools.list_changed` event. A comment on that PR claims "Charm and VScode support the spec." That claim was not checked against VS Code or Charm source. Merge state was not on the snippet that was opened. — [PR #5913](https://github.com/anomalyco/opencode/pull/5913)
- `mcp-use` documents server helpers `server.sendToolsListChanged()` and `server.sendNotification('notifications/tools/list_changed')` after adding a tool. That is a server-side send API, not a client that reloads. — [mcp-use notifications](https://www.mintlify.com/mcp-use/mcp-use/typescript/server/notifications)

### Inferences
- For the GitHub server at `v0.31.0`, a pre-`2026-07-28` client that handles `notifications/tools/list_changed` (Zed, Hermes) can see tools added by `enable_toolset` without reconnecting, because `AddTool` notifies legacy sessions unconditionally when list-changed is on. A `2026-07-28` client that never opens `subscriptions/listen` with `toolsListChanged: true` will not be told, even though `tools/list` would return the new set if the client asked again.
- The 2026-07-28 sentence that the tool list MUST NOT change "as a side effect of other requests on the connection" is in tension with `enable_toolset`, which changes the list as the side effect of a `tools/call`. GitHub's removal of the feature (2026-05-20) predates that spec date as written on the current tools page (2026-07-28). The pages do not say the spec sentence is why GitHub deleted the flag.

### Gaps
- Whether `github-mcp-server` at `v0.31.0` overrode `Capabilities.Tools.ListChanged` to false was not checked. The Go SDK default is to send. If that binary set `ListChanged: false`, `AddTool` would not notify.
- No primary VS Code, Claude Code, Cursor, or Charm doc was opened that says those hosts reload tools on `notifications/tools/list_changed`.
- OpenCode PR #5913 merge state was not confirmed.
- `mcpland/dynamic-mcp` says it notifies clients and does not name the method on the page that was opened.

## What does Hermes agent PR 3812 do on `notifications/tools/list_changed`?

### Takeaway
The page loaded. Merged PR #3812 makes Hermes, on `ToolListChangedNotification` only, re-fetch the server's tool list and replace that server's previously registered tools, with no reconnect, no gateway restart, and no `/mcp refresh`. Prompt and resource list-changed notifications are logged and not applied.

### Cited Findings
- [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812) ("feat(mcp): dynamic tool discovery via notifications/tools/list_changed", @teknium1) merged 2026-03-29 into main as commit `d5d22fe`. It says it implements the spec notification handler. The stated example is GitHub MCP with `GITHUB_DYNAMIC_TOOLSETS=1`. Salvaged from PR #1794 by @shivvor2. — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)
- On notification, `MCPServerTask._make_message_handler()` dispatches by type. `ToolListChangedNotification` triggers a refresh. Prompt and resource list changes are "logged stubs". — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)
- `MCPServerTask._refresh_tools()` does a nuke-and-repave under `_refresh_lock`: fetch the new tool list, remove the old tools from the registry and from `hermes-*` toolsets, then re-register the fresh list. `ToolRegistry.deregister(name)` removes a tool and drops the toolset check if it was the last tool in that toolset. `_register_server_tools()` is the shared helper for both initial discovery and this refresh (filtering, collision guards, utility tools, toolset creation, `hermes-*` injection). — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)
- `message_handler` is passed into all three `ClientSession` construction sites: stdio, new HTTP, and deprecated HTTP. `_check_message_handler_support()` inspects the `ClientSession` constructor so an older Python MCP SDK that lacks `message_handler` degrades to the previous static discovery. Missing notification types also degrade silently. No new config key. `mcp_servers` config is unchanged. — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)
- New tests in `tests/tools/test_mcp_dynamic_discovery.py` cover registration into `hermes-*`, a full refresh cycle (old removed, new registered), message-handler dispatch, and `deregister()` edge cases. The PR says 8 tests. A later blob of that test file shows `test_dispatches_tool_list_changed` building a `ToolListChangedNotification(method="notifications/tools/list_changed")` and expecting `_schedule_tools_refresh`. — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812); [test_mcp_dynamic_discovery.py](https://github.com/nousresearch/hermes-agent/blob/43b8951beb4495aaaf33e6ef0d88917a1c3e9c9e/tests/tools/test_mcp_dynamic_discovery.py)
- The PR does not add a `query` argument, does not read `tools.filtering`, and does not itself add or remove tools on the server. It only refreshes Hermes's copy of whatever list the server returns after the notification. — [PR #3812](https://github.com/NousResearch/hermes-agent/pull/3812)

### Inferences
- A client can see a newly enabled GitHub toolset without reconnecting only for a Hermes build that includes this PR (main after 2026-03-29) and only while the server still emits the notification. Current `github/github-mcp-server` main no longer has the flag the PR uses as its example (removed 2026-05-20).
- Hermes does not filter `tools/list`. It replaces the whole registered set for that server. A server that only answers a search query would look, to Hermes, like a list change of the entire catalog, because the handler does not diff by query.

### Gaps
- The PR page's file diff did not finish loading ("There was an error while loading"). The behavior above is from the PR summary and the commit message on that page, plus the test file blob, not from a line-by-line read of `tools/mcp_tool.py` on main after later commits.
- Whether current Hermes main still has this handler, or whether it opens a `subscriptions/listen` stream for protocol `2026-07-28`, was not checked.

## Is there an implementation of `tools.filtering` or a `query` argument on `tools/list`?

### Takeaway
No. The only spec change that adds `tools.filtering` and `query` on `tools/list` is SEP-1821 / PR #1822, and that PR was closed unmerged on 2026-06-13. Code search of `org:modelcontextprotocol` for `tools.filtering` returned zero files. Nothing opened implements that capability. Meta-tools such as `search_tools` and `enable_toolset` are a different mechanism and are not a `query` argument on `tools/list`.

### Cited Findings
- Proposed shape, never merged: `ListToolsRequestParams` gains `query?: string`. `ServerCapabilities.tools.filtering?: boolean`. Server behavior: declare `tools.filtering: true`; if `query` is set, return a filtered subset; if `query` is absent, return all tools. The server chooses substring, semantic, or tag matching. `query` is specified as plain text, not a structured query language. — [Issue #1821](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1821); [PR #1822](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1822)
- PR #1822 is closed. @localden closed it 2026-06-13 for lack of a sponsor. — [PR #1822](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1822)
- `tools.filtering org:modelcontextprotocol` code search: 0 results on 2026-10-03. — GitHub MCP `search_code`
- Current Go SDK `(*Server).listTools` paginates `req.Params` into `ListToolsResult`. The handler that was read does not branch on a search string. — [server.go `listTools`](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/refs/heads/main/mcp/server.go)
- The published `2025-06-18` `tools/list` request example contains only an optional `cursor`. — [tools.mdx 2025-06-18](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/server/tools.mdx)
- SEP-1300 (groups and tags filter on `tools/list`) is a different proposal. Its issue is labeled rejected. Its schema PR #1301 is closed. The TypeScript SDK draft [PR #840](https://github.com/modelcontextprotocol/typescript-sdk/pull/840) says it was not expected to be merged and was closed 2025-11-08. It is not `tools.filtering` from SEP-1821. — [Issue #1300](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1300); [typescript-sdk PR #840](https://github.com/modelcontextprotocol/typescript-sdk/pull/840)
- Nearby mechanisms that are not this feature: Speakeasy tag filtering is a `tags` URL parameter on the MCP server URL, not a `tools/list` param ([Speakeasy tag filtering](https://www.speakeasy.com/docs/ai-control-plane/distribute/mcp-servers/tool-filtering)). `respawn-app/tool-filter-mcp` is a proxy with a regex `--deny` list ([tool-filter-mcp](https://github.com/respawn-app/tool-filter-mcp)). C# SDK "filters" are server middleware (`AddListToolsFilter`), not the capability flag ([csharp-sdk filters.md](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/filters.md)). SEP-1881 is scope-filtered discovery (omit tools the token cannot call), and its text says search such as SEP-1821's `query` must not reveal tools outside the authorized set; it does not add `query` ([Issue #1881](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1881)).

### Inferences
- Anyone shipping "dynamic tool discovery" today is either mutating the registered set and sending `notifications/tools/list_changed`, or hiding the catalog behind meta-tools (`search_tools`, `enable_toolset`, `search-actors`). Neither one is SEP-1821.
- A client cannot discover `tools.filtering` by reading current server capabilities from the official schema, because that field was never merged.

### Gaps
- `ListToolsParams` in the Go SDK was not opened as a struct definition. The list handler does not consult a query; a dead field that nothing reads would not have shown up there. Combined with the closed PR and the empty org code search, there is still no implementation to cite.
- The `2026-07-28` tools page was not read end-to-end for the `tools/list` params example. The portion that was returned documents `listChanged` and the notification, not a `query` field.
