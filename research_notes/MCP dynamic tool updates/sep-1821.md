# SEP-1821 Dynamic Tool Discovery

SEP-1821 proposes an optional text search on `tools/list` plus a server capability flag. It did not ship. Issue #1821 is closed but still labeled only `proposal` and `SEP`, and its own header still says Status: Draft. Pull request #1822 is closed and not merged. The tools pages for revisions `2025-11-25`, `2026-07-28`, and `draft` have no `query` parameter on `tools/list` and do not mention a `filtering` capability.

## What does SEP-1821 propose, including the abstract and the exact new fields?

### Takeaway
SEP-1821 (Dynamic Tool Discovery) would let a client pass an optional plain-text `query` on `tools/list` and would add an optional boolean `ServerCapabilities.tools.filtering` so the client can tell whether the server will honor that parameter. The unmerged PR encodes those two fields and no others.

### Cited Findings

Adds `ServerCapabilities.tools.filtering` to indicate support, enabling agents to know when they can request filtered tool subsets."

ListToolsRequestParams": `ListToolsRequestParams` extends `PaginatedRequestParams` with `query?: string`, described as an optional search string the server interprets as simple text (category, tag, semantic description, or use-case scenario), and explicitly "NOT for complex JSON or structured queries." — [SEP-1821: Dynamic Tool Discovery](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1821)
- Exact capability flag, under heading "2. ServerCapabilities.tools.filtering": `tools?: { filtering?: boolean }`. Present means the server supports and will process `query`. ## How does the SEP say this interacts with `notifications/tools/list_changed`?

### Takeaway
The SEP does not change the notification. It says the client keeps the search string and, when `notifications/tools/list_changed` arrives, calls `tools/list` again with that same `query`, so the server returns only the current matching subset.

### Cited Findings
- Under heading "5. Interaction with List Change Notifications", the SEP's own wording is: "Search works seamlessly with `notifications/tools/list_changed`." The following code stores a query, calls `tools/list` with `{ query: searchQuery }`, and on `notifications/tools/list_changed` repeats that call. The comment in the snippet says the client "only receives updated matching tools, not full catalog." Benefits listed there: "Reduces bandwidth on re-fetches"; "Client maintains search result consistency"; "Server only sends matching tools, even after changes." Server behavior when tools change: "1. Send `notifications/tools/list_changed` (if `tools.listChanged: true`) 2. Next `tools/list` request applies same search logic 3. Returns current matching subset." — [SEP-1821: Dynamic Tool Discovery](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1821)
- The PR summary's corresponding line is "Works with notifications: Combines naturally with `tools.listChanged` for dynamic updates." — [SEP-1821: Add dynamic tool search support](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1822)
- The published "List Changed Notification" sections that were opened still describe only the bare notification `notifications/tools/list_changed` and a following unfiltered `tools/list`. They do not mention a stored query. On `2025-11-25` the server should send the notification when it declared `listChanged`. On `2026-07-28` and `draft` the server should send it to clients that opened a `subscriptions/listen` stream with `toolsListChanged: true`. — [Tools (2025-11-25)](https://modelcontextprotocol.io/specification/2025-11-25/server/tools); [Tools (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Tools (draft)](https://modelcontextprotocol.io/specification/draft/server/tools)

### Inferences
- Interaction, as the SEP writes it, is client-side reuse of the query on the next list request. The notification stays a signal with no tool list and no query in it. Nothing in the quoted section makes `list_changed` carry a filtered catalog.

### Gaps
- The SEP section is a sentence, a code sample, and two lists. It does not contain a longer prose paragraph than the sentence quoted above. No normative rule in that section says the server must remember the client's last query; the client re-sends it.
