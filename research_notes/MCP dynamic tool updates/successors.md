# Successors to SEP-1821 (dynamic tool discovery)

Scope is the texts that still try to do SEP-1821's job after it: an agent finds a tool without receiving the whole catalog, and a server changes what is visible while connected. Pages opened: [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636), [PR 1862](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1862), [progressive-disclosure-wg issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18), and the tools page of spec revision 2026-07-28. SEP-1881 and SEP-2564 are named inside PR 2636 but their texts were not opened.

## What does SEP-2636 (PR 2636, Tool Manifests) add, what does it say about SEP-1821, and did it merge?

### Takeaway
SEP-2636 was not merged. Closed on 2026-09-22 by a maintainer so it could be redone inside a working group. Its final description is an incremental fetch (`tools/manifest` plus `tools/describe`), not a search, and it says it is orthogonal to SEP-1821 because it has no query.

### Cited Findings
- PR title is "SEP-2636: Tool Manifests for Incremental Catalog Synchronization". GitHub records `state: closed`, `merged: false`, `closed_at: 2026-09-22T12:38:23Z`, opened 2026-04-23 by SylonZero, base `main`, head `SylonZero/modelcontextprotocol` branch `sep/progressive-tool-disclosure`. The description says it is seeking a sponsor. — [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636)
- What it adds, in the PR description: `tools/manifest` returns a compact entry per tool (name, optional title, required `digest` as `sha256:<hex>`, required byte `size`, optional annotations, no schemas). `tools/describe` returns full `Tool` definitions for an explicitly named subset in one round trip. One capability, `tools.manifest`, advertises both. `tools/list` stays the compatibility floor. The manifest and `tools/list` MUST return the same set for a session, and every manifest name MUST be describable. The digest is over the whole `Tool` under RFC 8785 canonical JSON. Unknown names on describe return JSON-RPC `-32602` with `data.unknownNames`. — [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636)
- On SEP-1821, the same description says: "Removed since the original draft: the `query` parameter (SEP-1821's territory)", and under relationships: "SEP-1821 (Dynamic Tool Discovery): orthogonal; this SEP carries no query surface." It also calls SEP-1862 (Tool Resolution), SEP-1881 (Scope-Filtered Discovery), and SEP-2564 (Server-Side Filtering) "orthogonal or compatible, as described in the SEP." — [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636)
- The description says the PR was originally titled "Progressive Tool Disclosure" and argued from context-token savings, then was rewritten in September 2026. It says the SEP makes no claim about model context tokens; host placement of definitions is a host concern. The problem it claims to solve is wholesale `tools/list` (full schemas every time) and `notifications/tools/list_changed` saying that something changed but not what. — [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636)
- Earlier review comments still discuss a query. On 2026-06-16 modood-alvi asked that unqueried `tools/catalog` equal `tools/list` and that a queried catalog be a subset. On 2026-09-12 the author replied that the then-current revision stated those three set relationships for `tools/catalog` with and without query. — [comment 4723308070](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-4723308070); [comment 5643460138](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-5643460138)
- Close, not merge. localden, 2026-09-22T12:38:24Z: "The MCP Maintainers and Core Maintainers met last week, and one of the changes we're making is that every new SEP should be developed with the help of a Working Group. ... I'm going to close this one out for now so it can go through that path. ... If the group decides to move forward, the result should be a SEP that can be opened once that decision is made." — [comment 5776646196](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-5776646196)
- After the close, the author (2026-09-26) said the working-group thread should surface the claims before redrafting the SEP. FreeOnePlus agreed the same day to bring evidence to the group before redrafting, and to keep collaborating on manifest/describe with deterministic grouping as an optional layer rather than open a competing proposal. — [comment 5842257742](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-5842257742); [comment 5843404223](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-5843404223)

### Inferences
- At close, SEP-2636 does not carry SEP-1821's search job. A client still receives one entry for every tool the session may see; it only avoids pulling every full schema, and it can see which definitions changed. The June–12 September comments show an earlier draft that did have a query on `tools/catalog`. The description at close says that query was removed and left to SEP-1821.
- Closing for process is not acceptance and not rejection of the design. No merged spec text came from this PR. `merged: false` is the GitHub field, not an inference.

## What is SEP-1862, and what does progressive-disclosure-wg issue 18 propose for tools/resolve?

### Takeaway
Two different `tools/resolve` proposals exist, and neither is in the published spec. SEP-1862 (closed, not merged, 2026-09-02) refines annotations of a tool the client already has, using the tool name plus intended arguments. Issue 18 (open, Apify, 2026-09-22) asks for `tools/resolve` by a list of names so a client can load full definitions that `tools/list` never returned. Issue 18 says `add-actor` plus `tools/list_changed` stopped working for most clients and is impossible under the stateless protocol.

### Cited Findings
- SEP-1862, PR title "SEP-1862: Tool Resolution", author SamMorrowDrums, opened 2025-11-21. GitHub records `state: closed`, `merged: false`, `closed_at: 2026-09-02T16:53:39Z`, labels `SEP` and `draft`, assignee `nickcoai`. It adds a `tools/resolve` method, a per-tool `resolve` field, and server capability `tools.resolve: true`. The stated problem is that `tools/list` definitions are static, so a multi-action tool must advertise `destructiveHint: true` even for a read. — [PR 1862](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1862)
- The request SEP-1862 proposes, quoted from the PR body: a client calls `tools/resolve` with the tool name and intended arguments before `tools/call`. The example request is `{ "method": "tools/resolve", "params": { "name": "manage_files", "arguments": { "action": "read" }}}`. The example response is `{ "tool": { "name": "manage_files", "annotations": { "readOnlyHint": true, "destructiveHint": false }}}`. The PR says the server returns a complete tool definition with annotations refined for that operation, following an LSP-style single preflight rather than separate preflight methods. — [PR 1862](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1862)
- Issue 18 is open. Jan Curn (`jancurn`) opened it on 2026-09-22 in `modelcontextprotocol/progressive-disclosure-wg`. It is a case study of Apify's marketplace of 70,000+ Actors and the remote server `mcp.apify.com`. The problem statement: they cannot put 70,000 definitions in `tools/list`, so they list about 20 core tools and clients use `search-actors(query)` to find more. — [issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18)
- Their claim, quoted: "Before MCP 2026-07-28, we provided an `add-actor(actorId)` tool that added the selected Actor to the tool list and sent the client a `tools/list_changed` notification. But most clients never supported this pattern, and now, with the new stateless protocol, it’s no longer possible." The workaround they describe is `call-actor(actorId, input)`, which collapses every Actor into one generic tool and drops per-tool schema validation, annotations, UI generation, and fine-grained approval. — [issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18)
- The proposed request, quoted from the issue: "Let's add a new client→server primitive message like: **`tools/resolve: { names: [...] } → { tools: [...] }`** where the response contains the same full `Tool` definitions as `tools/list`, with pagination, etc." The issue says this is "somewhat similar to earlier SEP-1862 and SEP-2636". The surrounding proposal is that `tools/list` be treated as non-exhaustive, that `tools/call` be allowed for tools that were not listed, and that a client which learns a name (from `search-actors`, a skill, or anything else) fetches the definition with `tools/resolve` and then either appends it to context or registers it in a progressive-discovery index. — [issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18)
- Issue 18 says discovery itself stays outside the protocol: "The suggested approach would give servers full control over how they want to implement the tool search. ... Our tool catalog is large and community-maintained, and simple grep or any other text-based search simply doesn't work well. We use dozens of other signals for filtering and ranking." — [issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18)

### Inferences
- Of the two `tools/resolve` shapes, only issue 18 does SEP-1821's job (learn a tool that was not in the catalog the client was given, and make it visible without a connection-scoped list mutation). SEP-1862 assumes the tool is already known and only changes annotations for a planned call.
- Issue 18 is a working-group issue, not a SEP pull request against the specification repo. It is open as of the page fetch. It is not a published specification.
- SEP-1862's close on 2026-09-02 is a close without merge. The reason for that close was not in the PR metadata.

### Gaps
- The comment that closed PR 1862 was not retrieved, so the close reason (withdrawn, dormant, rejected, or inactive) is unknown. Labels still included `draft` at retrieval.
- No later SEP that supersedes 1862 was opened in this pass. PR 2636 only lists 1862 as orthogonal or compatible.
- Issue 18's claim that "most clients never supported" `add-actor` plus `tools/list_changed` is the author's report. No client survey was opened to check it.

## Which mechanisms on the published 2026-07-28 tools page change or subset the tool list?

### Takeaway
On the published tools page, the list can change over time via `notifications/tools/list_changed` after a client subscribes, and it may differ by the authorization on the request. It must not change per connection or as a side effect of another request. Pagination and cache TTL are present. `query`, `filtering`, `manifest`, `tools/describe`, and `tools/resolve` are absent.

### Cited Findings
- Servers that support tools MUST declare the `tools` capability. The documented flag is `listChanged`. "`listChanged` indicates whether the server will emit notifications when the list of available tools changes." — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- The set rule, quoted from that page: servers MUST respond to `tools/list` with the tools currently available to the requesting client. "This set MAY be empty and MAY change over time (see List Changed Notification), but MUST NOT vary per-connection or as a side effect of other requests on the connection. The set MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit — since credentials are per-request input, not connection state." — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Change signal: servers that declared `listChanged` SHOULD send `notifications/tools/list_changed` to clients that have opened a `subscriptions/listen` stream with `toolsListChanged: true`. The message flow then has the client call `tools/list` again. The notification body on the page is `{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }`. — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- `tools/list` on that page takes `cursor` and the example result includes `nextCursor`, `ttlMs` (example `300000`), and `cacheScope` (example `"public"`). The page says the operation supports pagination and caching. Servers SHOULD return tools in a deterministic order so clients can cache the list. — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- A client-side subset, not a server query: for Streamable HTTP, if an `x-mcp-header` value breaks the constraints, the client MUST reject that tool definition, and "Rejection means the client MUST exclude the invalid tool from the result of `tools/list`." — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- The same page, in a non-normative "Stateful Tools" note: "MCP has no protocol-level session, so a server cannot rely on implicit per-connection state to relate one tool call to the next." Handles are ordinary strings in results and later arguments. — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Absent from this page: a `query` parameter on `tools/list`, a `filtering` capability, `tools/manifest`, `tools/describe`, `tools/catalog`, and `tools/resolve`. The only list request parameters shown are the cursor. The only tool methods shown are `tools/list` and `tools/call`. — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences
- The published page agrees with the part of Apify's claim that is about the protocol: a server cannot add a tool to the visible set as the side effect of a call such as `add-actor` on that connection. The "most clients never supported this" half is not something this page can confirm.
- Authorization-scoped `tools/list` is the only published way to return a subset. It is not search. The client does not send a query; the server keys the set off credentials on that request.
- Pagination subsets bytes per response, not the catalog. The client is still expected to walk the full set. `ttlMs` / `cacheScope` say how long to trust a result; they do not select tools.

### Gaps
- The linked pagination, caching, and `subscriptions/listen` pages were not opened. Anything those pages add beyond the sentences and examples on the tools page is unchecked.
- The SEP index was not opened, so this note does not independently prove that no other final SEP mentions `tools/resolve`. The claim of absence is limited to the 2026-07-28 tools page.

## What can a server do today, in the published spec, to change its tool list mid-session, and what is still only a proposal?

### Takeaway
In spec revision 2026-07-28, a server may change the tool set over time and, if it advertised `tools.listChanged`, SHOULD tell clients that subscribed with `subscriptions/listen` (`toolsListChanged: true`) by sending `notifications/tools/list_changed`; those clients then call `tools/list` again. The same page allows the returned set to depend on the authorization presented on that request, and it allows cursor pagination and a cache TTL (`ttlMs`, `cacheScope`). It forbids the set from varying per connection or as a side effect of another request on the connection, and a non-normative note says MCP has no protocol-level session. So an in-connection "add this tool and notify" update is not allowed, and there is no way for the client to ask for a named tool or a search hit that was never listed. Still proposals, none merged: SEP-2636's `tools/manifest` and `tools/describe` (closed unmerged 2026-09-22; same full name set as `tools/list`, no query, explicitly orthogonal to SEP-1821), SEP-1862's argument-specific `tools/resolve` (closed unmerged 2026-09-02; refines annotations of a known tool), and the open Apify request in progressive-disclosure-wg issue 18, `tools/resolve: { names: [...] } → { tools: [...] }`, which is the one text that again lets a server keep `tools/list` non-exhaustive and let a client pull definitions by name after its own search.

### Cited Findings
- Published change and subset rules are the `listChanged` notification, the MUST NOT per-connection / side-effect sentence, the MAY-vary-by-authorization sentence, cursor pagination, and `ttlMs` / `cacheScope`, all on the tools page cited above. `query`, `filtering`, manifest, and `tools/resolve` are absent there. — [Tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- SEP-2636 is closed and not merged; its description disclaims a query and points that job back at SEP-1821. — [PR 2636](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636); [close comment](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2636#issuecomment-5776646196)
- SEP-1862 is closed and not merged; its `tools/resolve` takes `name` and `arguments` and returns a refined tool, not a catalog slice. — [PR 1862](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1862)
- The name-list `tools/resolve` and the `add-actor` / stateless claim are in the open working-group issue, not in a specification PR that merged. — [issue 18](https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18)

### Inferences
- "Change the list mid-session" survives only as a time-based change plus a subscription notification, or as a different answer for a different credential. It does not survive as session state mutated by a tool call. That is why the proposals after 2026-07-28 split into cache reconciliation (2636) and fetch-by-name for tools the list omitted (issue 18), instead of another `list_changed` side effect.
- None of 1862, 2636, or issue 18 is a published spec mechanism as of the pages opened on 2026-10-03.

### Gaps
- SEP-1821's own close or dormant state was not re-opened here. PR 2636 still treats it as the owner of the query surface, which is evidence it was not the mechanism on the 2026-07-28 tools page, not evidence of its issue status.
- No check was made for a SEP opened after 2026-09-26 that might have replaced 2636 or issue 18.
